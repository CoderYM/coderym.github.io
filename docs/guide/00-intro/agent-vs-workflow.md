# Agent、Chatbot 与 Workflow 的区别

::: info 学习目标
- 用「谁决定下一步」这一个问题区分 Chatbot、Workflow、Agent
- 了解五种常见 Workflow 模式，以及它们和 Agent 的关系
- 掌握一套选型决策方法：什么时候不该用 Agent
- 理解实际系统往往是三者的混合
:::

## 三种形态一张表

| 维度 | Chatbot | Workflow | Agent |
| --- | --- | --- | --- |
| 谁决定下一步 | 用户（每轮由人推进） | 开发者写好的代码 | 模型自己 |
| 是否调用工具 | 通常没有或很少 | 有，在固定节点调用 | 有，由模型选择调用哪个、调几次 |
| 步骤数 | 一问一答 | 固定或有限分支 | 动态，事先不确定 |
| 可预测性 | 高 | 高 | 低 |
| 成本与延迟 | 低 | 中，可估算 | 高，波动大 |
| 调试难度 | 低 | 中 | 高，需要轨迹追踪 |
| 典型场景 | 客服问答、写作助手 | 文档抽取、报表生成、审批流 | 编程助手、深度研究、运维排障 |

一句话记忆：**Chatbot 是人在驾驶，Workflow 是轨道列车，Agent 是自动驾驶**。

## Chatbot：人推动每一步

Chatbot 的核心是多轮对话。模型每次只回答当前这一轮，下一步做什么由用户决定。

```text
用户 ──▶ LLM ──▶ 回复 ──▶ 用户看完再提问 ──▶ LLM ──▶ ...
```

它可以很强大（长上下文、联网搜索、上传文件），但主动权始终在人手里。很多所谓「AI 助手」本质是 Chatbot，加了一两个工具也不改变这一点。

## Workflow：代码编排 LLM

Workflow 把任务拆成预先定义的步骤，LLM 是其中的若干节点。Anthropic 在《Building effective agents》里总结了几种常见模式：

| 模式 | 结构 | 适用场景 |
| --- | --- | --- |
| Prompt Chaining（链式） | A → B → C，上一步输出作为下一步输入，中间可插入校验 | 先写大纲再写正文；先翻译再润色 |
| Routing（路由） | 分类器决定走哪条分支 | 客服问题分类后交给不同处理流程 |
| Parallelization（并行） | 同一任务拆成多份并行，或多次投票 | 长文档分段摘要；多次审查取多数 |
| Orchestrator-Workers（编排者-工人） | 一个 LLM 动态拆解子任务，分发给多个 LLM 执行 | 修改涉及多个文件的代码 |
| Evaluator-Optimizer（评估-优化） | 生成 → 评估 → 根据反馈改进，循环若干轮 | 翻译润色、代码按测试修复 |

以「合同信息抽取」为例，一个典型 Workflow：

```text
PDF ──▶ 解析文本 ──▶ LLM 抽取字段 ──▶ Schema 校验 ──┬─ 通过 ──▶ 入库
                                                  └─ 失败 ──▶ 带错误重试（最多 2 次）──▶ 人工审核
```

每一步做什么、失败怎么办，全部写在代码里。这让它**可测试、可估算成本、出了问题容易定位**。

注意后两种模式已经让 LLM 掌握了部分控制权，它们处在 Workflow 和 Agent 之间。这正说明两者是连续的光谱，而不是二选一。

## Agent：模型掌握控制流

Agent 把「下一步做什么」交给模型。开发者提供的是工具、目标、约束和终止条件，而不是步骤。

```text
目标 ──▶ ┌─▶ LLM 决策 ──▶ 调用工具 ──▶ 观察结果 ─┐
         └──────────────────────────────────────┘ ──▶ 完成 / 达到上限
```

以「修复一个线上 Bug」为例：Agent 可能先搜日志，发现异常后读相关代码，再跑测试复现，修改代码，再跑测试。这个路径事先无法写死，因为每一步都依赖上一步的发现。这正是 Agent 的价值所在。

代价同样明显：同一个任务跑两次，步骤可能不同；某次可能多花 3 倍 Token；模型可能走进死胡同。所以 Agent 必须配套评估、追踪、预算控制，这些内容在 [14 评估与可观测性](/guide/14-evaluation/why-evals) 和 [15 安全与生产化](/guide/15-production/permissions-hitl) 里展开。

## 选型：从最简单的方案开始

一个实用的决策顺序：

```text
1. 一次 LLM 调用（加好的提示词、检索）能解决吗？  ── 能 ──▶ 就用它
                │ 不能
2. 步骤能事先列清楚吗？                         ── 能 ──▶ Workflow
                │ 不能，路径依赖中间结果
3. 错误代价可控吗？有评估手段吗？                ── 否 ──▶ 先补评估 / 加人工审核
                │ 是
4. 用单 Agent，设好工具、步数和预算上限
                │ 单 Agent 上下文装不下，或职责差异很大
5. 考虑多 Agent
```

判断「步骤能否事先列清楚」时，可以问自己：**如果让一个新同事做，我能写一份固定 SOP 吗？** 能写，就优先 Workflow；SOP 里充满「视情况而定」，Agent 才有意义。

## 现实系统是混合的

生产系统很少是纯粹的某一种：

- 一个客服系统整体是 Chatbot，但「退款」意图会路由到一个固定 Workflow，「复杂故障排查」再交给一个 Agent。
- 一个 Agent 的某个工具内部，可能就是一个确定性的 Workflow（例如「生成并校验报表」）。
- LangGraph 这类框架的思路正是把 Workflow 的确定性和 Agent 的灵活性组合在一张图里，详见 [LangGraph](/guide/11-frameworks/langgraph)。

把它们当作工具箱里的三种工具，而不是三个互斥的阵营。

## 常见坑

- **为了「Agent」而 Agent**。用 Agent 实现一个固定三步流程，结果更慢、更贵、更不稳定。
- **把 Workflow 写成巨大的 if-else 来模拟灵活性**。分支爆炸时，说明这部分可能该交给模型决策。
- **只在 Demo 上比较**。Agent 在演示里常常很惊艳，但要用几十上百条真实样例评估成功率和成本后再决定。
- **忽略混合方案**。不必整个系统都是 Agent，只在真正需要动态决策的环节用 Agent。

## 小测

**1. 「每天早上抓取 10 个固定网站的新闻，逐条摘要后汇总成日报发邮件」，适合用 Agent 还是 Workflow？**

::: details 查看答案
Workflow。步骤固定（抓取 → 摘要 → 汇总 → 发送），可以并行摘要（Parallelization 模式）。用 Agent 只会增加成本和不确定性。
:::

**2. Orchestrator-Workers 模式和 Agent 有什么相同和不同？**

::: details 查看答案
相同点：都由 LLM 动态决定任务如何拆解。不同点：Orchestrator-Workers 的整体结构（先拆解、再分发、再汇总）是固定的，通常一次拆解就结束；Agent 则在开放循环中持续根据观察结果决定下一步，步数和路径都不固定。
:::

**3. 你的 Agent 在演示中效果很好，上线前最应该补哪件事？**

::: details 查看答案
建立评估集，用一批真实任务批量运行，统计成功率、平均步数、Token 成本和失败类型。同时加上步数、预算上限和轨迹追踪。没有评估就无法知道改动是变好还是变坏。
:::
