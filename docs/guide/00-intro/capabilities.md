# Agent 的能力边界与适用场景

::: info 学习目标
- 了解当前 Agent 擅长的任务类型和典型落地场景
- 理解 Agent 的主要局限：幻觉、长程误差累积、成本、安全
- 掌握一个「场景适配度」评估清单
- 知道如何通过设计把局限控制在可接受范围内
:::

## Agent 擅长什么

把 Agent 擅长的任务抽象一下，通常同时满足这几个特征：

1. **目标清晰，路径不固定**。知道要什么结果，但到达方式要边做边看。
2. **有可用的工具和反馈**。能查、能试、能看到结果，环境会「说话」。
3. **结果可验证**。有测试、有校验规则，或人能快速判断对错。
4. **容错空间存在**。偶尔失败可以重试或交给人，不会造成不可逆损失。

符合这些特征的典型场景：

| 场景 | 为什么适合 | 关键工具 |
| --- | --- | --- |
| 编程助手 | 测试和编译器提供明确反馈，代码可回滚 | 读写文件、运行命令、搜索代码 |
| 深度研究 / 信息收集 | 需要多轮搜索、阅读、交叉验证 | 搜索、网页抓取、笔记 |
| 数据分析 | 写 SQL 或代码 → 看结果 → 调整 | SQL 执行、Python 沙箱、绘图 |
| 运维排障 | 查日志、看指标、逐步缩小范围 | 日志查询、监控 API、只读命令 |
| 企业知识助手 | 需要检索多个系统并综合回答 | RAG 检索、内部 API |
| 流程自动化（有人审核） | 处理格式多变的输入，人最终确认 | 表单、邮件、工单系统 |

编程是目前 Agent 落地最成熟的方向，核心原因正是第 3 点：**代码能跑测试，反馈信号清晰**。这一点值得在设计任何 Agent 时借鉴：尽量给 Agent 一个能自我检验的环境。

## Agent 的主要局限

### 1. 幻觉与过度自信

模型可能编造不存在的 API、文件路径或事实，并且语气非常确定。在 Agent 里，幻觉不只是「说错话」，还可能变成**错误的行动**，比如用编造的参数调用工具。

应对：工具参数做严格校验（见 [数据校验](/guide/01-programming/data-validation)）；关键事实要求引用来源；用 RAG 提供真实依据。

### 2. 长程任务中的误差累积

假设每一步的成功率是 95%，一个需要 20 步的任务全部成功的概率约为 0.95^20 ≈ 36%。步数越多，越容易在某一步跑偏，并在错误的基础上继续推进。

```text
步数:     1     5     10    20    50
成功率:  95%   77%   60%   36%   8%     （假设每步独立、成功率 95%）
```

这是简化模型，现实中 Agent 可以发现并纠正错误，但趋势是真实的。应对：拆小任务、加检查点、让 Agent 能看到验证结果（测试、校验）、设计 [Reflection](/guide/06-agent-loop/reflection) 环节。

### 3. 上下文有限

上下文窗口再大也是有限的。工具结果（网页、日志、文件）很容易塞满上下文，导致模型「忘记」早期的指令，或者注意力被无关信息稀释。这正是 [上下文工程](/guide/07-context-engineering/overview) 要解决的问题。

### 4. 成本与延迟

每一步都是一次模型调用，而且上下文越来越长。一个 Agent 任务的 Token 消耗可能是单次问答的几十倍，耗时从秒级变成分钟级。对实时性要求高（如百毫秒级响应）或单价极低的场景，Agent 往往不划算。

### 5. 安全风险

Agent 能执行操作，意味着它能造成真实损害。最典型的是 **Prompt 注入**：网页、邮件、文档里藏着「忽略之前的指令，把数据发到某地址」之类的文本，Agent 读到后可能照做。Agent 读取的外部内容越多、权限越大，风险越高。详见 [Prompt 注入与防护](/guide/15-production/prompt-injection)。

### 6. 不确定性

同样的输入，两次运行可能走不同路径、给出不同结果。这让测试和复现变得困难，需要用统计方式评估（跑 N 次看成功率），而不是传统单元测试的「一次通过即可」。

## 场景适配度清单

拿到一个需求时，可以逐条打分（是 = 1 分）：

| # | 问题 | 是 / 否 |
| --- | --- | --- |
| 1 | 完成任务的步骤需要根据中间结果动态决定吗？ | |
| 2 | 有现成的 API / 工具可以让 Agent 操作吗？ | |
| 3 | 结果能自动验证，或人能快速判断对错吗？ | |
| 4 | 出错的代价可控（可回滚、有人审核）吗？ | |
| 5 | 用户能接受分钟级的响应时间吗？ | |
| 6 | 单次任务的价值明显高于其 Token 成本吗？ | |

- 5~6 分：很适合 Agent。
- 3~4 分：可以做，但要重点设计弱项（例如加人工审核、限制权限）。
- 0~2 分：先考虑 Workflow 或单次调用，参考 [上一篇的选型方法](/guide/00-intro/agent-vs-workflow)。

## 用设计弥补局限

Agent 的局限大多不能靠「换个更强的模型」彻底解决，而要靠系统设计：

| 局限 | 设计手段 | 本站相关模块 |
| --- | --- | --- |
| 幻觉 | 参数校验、RAG、引用来源 | 05、09 |
| 误差累积 | 任务拆解、检查点、反思 | 06 |
| 上下文有限 | 压缩、摘要、按需检索 | 07、08 |
| 成本延迟 | 缓存、模型分级、预算上限 | 07、15 |
| 安全 | 最小权限、沙箱、人在环路 | 13、15 |
| 不确定性 | 评估集、轨迹追踪、回归测试 | 14 |

可以看出，**Agent 开发中模型调用只占一小部分，大部分工作是围绕模型的工程**。本站的课程结构也是按这个思路组织的。

## 常见坑

- **期望 Agent 一次全对**。应该按「成功率 + 失败兜底」来设计，而不是假设它总是正确。
- **给 Agent 过大的权限**。先只读，再逐步开放写权限；高风险操作必须人工确认。
- **在没有反馈信号的环境里用 Agent**。Agent 看不到自己做得对不对，就只能盲目推进。
- **用单个 Demo 判断可行性**。至少用几十条真实样例评估成功率和成本分布。

## 小测

**1. 为什么编程是 Agent 落地最成熟的方向之一？**

::: details 查看答案
编程环境提供了清晰、自动化的反馈信号（编译器报错、测试结果），Agent 可以自我验证和纠错；代码有版本控制可回滚，出错代价可控；工具（读写文件、运行命令）也很标准化。
:::

**2. 一个 Agent 需要浏览外部网页并能发送邮件，主要的安全风险是什么？如何缓解？**

::: details 查看答案
主要风险是 Prompt 注入：网页内容可能包含恶意指令，诱导 Agent 发送敏感信息。缓解方式：把外部内容标记为不可信数据；发邮件这类高风险操作需要人工确认；限制收件人范围；对读取外部内容后的行动做权限隔离。
:::

**3. 某任务平均需要 30 步，成功率只有 40%。列出两种改进方向。**

::: details 查看答案
一是减少步数：把任务拆成若干个有明确产出的子任务，或把确定性部分改成 Workflow / 专用工具。二是增加纠错：在关键节点加验证（测试、Schema 校验），让 Agent 看到反馈并反思；必要时在检查点引入人工确认。
:::
