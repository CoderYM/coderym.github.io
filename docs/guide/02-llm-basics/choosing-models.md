# 如何选择模型

::: info 学习目标
- 掌握模型选型的关键维度：能力、延迟、成本、上下文、合规与部署
- 理解闭源 API、开源权重、本地部署各自的取舍
- 学会用"小评估集 + 实测"代替看排行榜做决策
- 知道如何在架构上为更换模型留出余地
:::

模型更新的速度很快，今天的"最强模型"几个月后可能就被超越。所以本文不推荐具体型号，而是给出一套**不会过时的选型方法**。真正决定选哪个模型的，应该是你自己的任务和数据，而不是排行榜或宣传。

## 选型维度

| 维度 | 要问的问题 | 说明 |
| --- | --- | --- |
| 任务能力 | 在我的任务上答得对吗？ | 通用排行榜只能参考，必须在自己的数据上测 |
| 指令遵循 | 能否稳定遵守格式和约束？ | 对 Agent 来说往往比"聪明"更重要 |
| Tool Calling | 工具选择和参数生成是否可靠？ | 决定能否做好 Agent，单独评估 |
| 延迟 | 首 Token 时间、生成速度是多少？ | 交互场景对首 Token 延迟敏感 |
| 成本 | 单次任务平均花多少钱？ | 按"每完成一个任务的成本"算，而不是看单价 |
| 上下文窗口 | 够不够装下我的典型输入？ | 窗口大不等于长文本效果好 |
| 多模态 | 需要看图、读 PDF、听语音吗？ | 见 [多模态输入](/guide/03-llm-api/multimodal) |
| 语言 | 中文表现如何？ | 中文场景务必用中文数据测试 |
| 合规与数据 | 数据能否出境？能否被用于训练？ | 企业场景常常是一票否决项 |
| 稳定性 | 限流额度、可用性、SLA 如何？ | 生产环境需要考虑多厂商容灾 |

## 模型的几种"档位"

不同厂商的命名各不相同，但产品线大致可以分为几档：

```text
         能力
          ▲
          │   ● 旗舰 / 推理模型：最强，最慢，最贵
          │
          │        ● 主力模型：能力与成本的平衡点
          │
          │              ● 轻量模型：快、便宜，适合简单任务
          │
          └──────────────────────────────▶ 速度 / 成本优势
```

一个常见的误区是"全部用最强的"。实际上，Agent 中的大量调用（意图分类、简单抽取、格式转换、摘要）用轻量模型就足够了。合理的做法是**分层使用**：

- **路由层**：用轻量模型判断请求类型和难度。
- **主流程**：用主力模型完成大部分对话和工具调用。
- **难点环节**：规划、复杂推理、代码修改交给旗舰或推理模型（见 [推理模型与扩展思考](/guide/02-llm-basics/reasoning-models)）。

## 闭源 API、开源权重与本地部署

| 方式 | 优点 | 缺点 | 适合 |
| --- | --- | --- | --- |
| 闭源 API | 能力通常领先，开箱即用，无需运维 | 数据需发送给厂商，受限流和价格调整影响 | 绝大多数应用的起点 |
| 云上托管开源模型 | 模型可选择、可迁移，价格通常较低 | 能力与顶尖闭源模型可能有差距 | 成本敏感、希望避免锁定 |
| 私有化部署开源模型 | 数据完全可控，可微调 | 需要 GPU 和推理运维能力，前期投入大 | 强合规、内网环境、高调用量 |

对大多数团队，建议的路径是：**先用闭源 API 快速验证产品可行性，在有了评估集和真实流量数据之后，再考虑是否迁移到更便宜或可私有化的方案**。过早投入私有化部署，往往会把精力消耗在运维上，而不是产品本身。

## 选型流程：用数据说话

```text
1. 明确任务 ──▶ 2. 构建小评估集 ──▶ 3. 圈定 3~5 个候选 ──▶ 4. 实测打分
                    (30~100 条)                               │
                                                              ▼
6. 上线后持续监控 ◀── 5. 综合质量、延迟、成本做决定 ◀──────────┘
```

**第 1 步：明确任务**。写清楚输入是什么、期望输出是什么、什么叫"做对"。例如"从用户邮件中抽取订单号和退款原因，输出 JSON"。

**第 2 步：构建小评估集**。从真实数据中挑选 30~100 条样本，覆盖常见情况和困难情况，标注期望结果。这一步最花时间，但也最有价值，后面的 [评估集与指标设计](/guide/14-evaluation/eval-design) 会详细展开。

**第 3 步：圈定候选**。根据合规要求、预算和语言先做一轮筛选。一般可以包括一个旗舰模型（作为能力上限的参照）、几个主力模型和一个轻量模型。

**第 4 步：实测打分**。用同样的提示词跑完评估集，记录：

- 正确率（或其他质量指标）
- 平均和 P95 延迟
- 平均每条的输入、输出 Token 和成本
- 格式错误率、工具调用错误率

**第 5 步：综合决策**。常见的结论形式是："轻量模型 A 正确率 91%，成本只有旗舰的十分之一，满足要求的 90% 阈值，选 A；把它答错的类型交给主力模型 B 兜底。"

**第 6 步：持续监控**。模型版本会更新，你的数据分布也会变化。评估集要变成回归测试的一部分，见 [回归测试与持续评估](/guide/14-evaluation/regression)。

## 为更换模型做好准备

模型选型不是一次性决策。为了让以后更换模型的成本最低，架构上可以：

1. **统一接口**：业务代码通过一层自己的封装调用模型，不直接散落着厂商 SDK 调用。使用 OpenAI 兼容接口能覆盖很多厂商，这也是本站示例统一使用它的原因（见 [主流模型厂商 API 对比](/guide/03-llm-api/providers)）。
2. **配置化**：模型名、Base URL、参数都放在配置里，不写死在代码中。本站示例使用的 `LLM_MODEL`、`OPENAI_BASE_URL` 就是这个思路。
3. **按任务配置模型**：不同环节可以使用不同模型，例如 `ROUTER_MODEL`、`PLANNER_MODEL`。
4. **提示词与模型解耦但一起测试**：同一提示词在不同模型上的效果可能差别很大，更换模型时要重新跑评估。

一个按任务配置模型的 `.env` 示例（模型名仅为示例）：

```bash
OPENAI_API_KEY=sk-...
OPENAI_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-chat
ROUTER_MODEL=deepseek-chat
PLANNER_MODEL=deepseek-reasoner
```

## 常见坑

- **只看排行榜**：公开基准可能和你的任务差别很大，还存在数据污染的问题。排行榜用于圈定候选，不用于最终决策。
- **只看单价**：单价低但需要多次重试、输出冗长或要额外纠错的模型，单次任务的总成本可能更高。
- **只试几个例子**：凭几次对话的"感觉"选模型，结论很容易被随机性误导。
- **忽略合规**：开发完才发现客户不允许数据出境，只能推倒重来。合规要求应在选型的第一步确认。
- **假设新版本一定更好**：模型升级后，某些任务的表现可能变差，格式习惯也可能变化。升级前先跑回归评估。
- **深度绑定单一厂商的专有特性**：不是不能用，但要清楚迁移成本，并尽量把它们封装在适配层里。

## 小测

**1. 模型 A 单价是模型 B 的一半，但在你的任务上 A 平均需要重试 1.5 次才能输出合法 JSON，B 一次成功。仅从 Token 成本看哪个更划算？**

::: details 查看答案
A 平均每个任务要调用约 2.5 次（1 次 + 1.5 次重试），按一半的单价算，成本约为 B 的 1.25 倍，而且延迟更高。所以 B 更划算。选型要按"每完成一个任务的成本"计算。
:::

**2. 一个面向银行内部的知识助手项目，选型时第一件要确认的事是什么？**

::: details 查看答案
合规与数据要求：数据能否发送到外部 API、是否必须私有化部署、对模型来源有什么要求。这些约束会直接决定候选范围，应该在比较能力之前确认。
:::

**3. 为什么建议在候选列表里放一个最强的旗舰模型，即使预算上并不打算用它？**

::: details 查看答案
它可以作为能力上限的参照。如果连旗舰模型在评估集上的表现都不理想，问题很可能出在任务定义、提示词或上下文上，而不是模型选择。如果旗舰模型表现很好，就能清楚看到便宜模型差距有多大，从而判断是否值得用更贵的模型。
:::
