# Transformer 的直觉理解

::: info 学习目标
- 理解大模型的本质：一个反复"预测下一个 Token"的函数
- 用直觉理解注意力（Attention）机制在做什么
- 知道训练、推理、预训练与指令微调分别是什么
- 能把这些原理和 Agent 开发中的实际现象对应起来
:::

做 Agent 开发不需要会推导 Transformer 的公式，但需要知道模型"大概是怎么工作的"。很多看起来奇怪的现象，比如模型会编造事实、长对话中忘掉前面的要求、同一个问题两次回答不一样，都能从原理里找到解释。这篇文章只讲直觉，不讲矩阵运算。

## 大模型只做一件事：预测下一个 Token

把大模型想成一个函数：输入一段文本，输出"下一个 Token 是什么"的概率分布。Token 是模型处理文本的最小单位，可以粗略理解为"词或词的一部分"，下一篇 [Token 与上下文窗口](/guide/02-llm-basics/tokens-context) 会详细展开。

```text
输入:  "北京是中国的"
            │
            ▼
      ┌───────────┐
      │  大模型    │
      └───────────┘
            │
            ▼
输出概率:  首都 0.82 | 城市 0.06 | 政治 0.04 | ...
```

模型选出一个 Token（比如"首都"），把它拼到输入末尾，再预测下一个，如此循环，直到生成结束标记或达到长度上限。这叫**自回归生成**（autoregressive generation）：

```text
第 1 步: 北京是中国的            → 首都
第 2 步: 北京是中国的首都        → 。
第 3 步: 北京是中国的首都。      → <结束>
```

这个简单的循环带来几个直接后果：

- **输出是一个一个 Token 生成的**。所以 API 可以流式返回（见 [流式响应实战](/guide/03-llm-api/streaming)），输出越长耗时越长。
- **每一步都是在概率中挑选**。挑选方式由 temperature、top_p 等参数控制（见 [采样参数](/guide/02-llm-basics/sampling)），这就是同一问题两次回答可能不同的原因。
- **模型没有"查数据库"这一步**。它生成的是"看起来最合理的续写"，而不是"经过核实的事实"。合理但错误的续写就是我们常说的幻觉（hallucination）。

聊天、写代码、调用工具，在模型眼里都是"续写文本"。Chat API 里的 system、user、assistant 消息，最终会被拼成一段带特殊标记的长文本交给模型续写。Tool Calling 也一样：模型续写出一段符合约定格式的 JSON，由你的程序去真正执行。

## 注意力：每个 Token 都在"看"其他 Token

预测下一个 Token 时，模型需要理解上下文。Transformer 的核心是**注意力机制**（Attention）：处理每个 Token 时，它会给前文中的每个 Token 打一个"相关度"分数，然后按分数加权汇总这些 Token 的信息。

看一个例子：

```text
"小王把书借给了小李，因为他明天要考试。"

处理 "他" 时，模型的注意力大致分布：
  小王 ████████░░  0.35
  小李 ██████████  0.45
  书   ██░░░░░░░░  0.08
  考试 ███░░░░░░░  0.12
```

"他"指谁需要结合整句话判断，注意力机制让模型在每一步都能动态决定"现在该重点看哪些词"。几个关键直觉：

1. **多头注意力**（Multi-Head Attention）：模型同时有很多组注意力，有的关注语法关系，有的关注指代，有的关注格式。每组叫一个"头"。
2. **层层堆叠**：一个 Transformer 由几十层甚至上百层这样的结构叠起来。浅层更多处理词语和语法，深层逐渐形成更抽象的语义。
3. **只能看前面**：生成式模型使用因果注意力（causal attention），每个 Token 只能看到它之前的内容，看不到"未来"。
4. **全部并行**：与早期的 RNN 逐字处理不同，Transformer 可以并行处理整段输入。这是它能在海量数据上训练的关键原因。

注意力的计算量随输入长度大约呈平方增长，所以上下文越长，推理越慢、越贵。这也是上下文窗口有上限的原因之一。

## 位置信息

注意力本身不关心顺序，"狗咬人"和"人咬狗"里的 Token 是一样的。所以模型会给每个 Token 附加位置信息（位置编码）。现代模型常用 RoPE 等相对位置编码方案，这也是厂商能把上下文窗口扩展到很长的技术基础之一。

开发中要知道的结论是：**模型对长上下文中不同位置的信息，利用程度并不均匀**。有研究发现模型更容易利用开头和结尾的信息，而中间部分容易被忽略（"Lost in the Middle"）。因此重要的指令放在 system prompt 开头或用户消息末尾，效果通常更稳定。

## 模型是怎么"学会"的

```text
┌────────────┐    ┌──────────────┐    ┌────────────────┐
│  预训练     │ →  │  指令微调     │ →  │  偏好对齐       │
│ 海量文本    │    │ 问答示范数据  │    │ RLHF / 偏好优化 │
│ 学会续写    │    │ 学会听指令    │    │ 学会更有帮助、  │
│            │    │              │    │ 更安全          │
└────────────┘    └──────────────┘    └────────────────┘
```

- **预训练**：在海量文本上反复做"预测下一个 Token"的练习。模型从中学到语言、知识和一定的推理模式。这一步得到的是"基座模型"（base model），擅长续写，但不一定听指令。
- **指令微调**（SFT）：用大量"指令 → 理想回答"的示范数据继续训练，模型学会以助手的方式回答。
- **偏好对齐**：通过人类或 AI 的偏好反馈继续优化，让回答更有帮助、更安全。工具调用、结构化输出这类能力也主要在微调阶段被专门强化。

训练完成后，模型的参数（权重）就固定了。你调用 API 时只是在做**推理**（inference），模型不会因为你的对话而"学习"。这一点很重要：

- 模型的知识停留在训练数据的截止时间（knowledge cutoff），需要新知识就得通过上下文提供，这就是 [RAG](/guide/09-rag/overview) 的出发点。
- 模型本身没有记忆。多轮对话"记得"前文，是因为每次请求你都把历史消息重新发了一遍（见 [多轮对话与消息结构](/guide/03-llm-api/multi-turn)）。跨会话的记忆需要你自己实现（见 [记忆的分类](/guide/08-memory/memory-types)）。

## 这些原理对 Agent 开发意味着什么

| 原理 | 实际现象 | 开发上的应对 |
| --- | --- | --- |
| 逐 Token 生成 | 输出越长越慢 | 用流式输出改善体验，控制 max_tokens |
| 概率采样 | 同样输入结果不同 | 需要稳定时降低 temperature，做评估而不是只试一次 |
| 续写"合理文本" | 幻觉、编造 API 名 | 用工具和检索提供事实，对输出做校验 |
| 注意力计算随长度增长 | 长上下文更贵、更慢 | 做上下文管理和压缩 |
| 位置利用不均 | 长对话中忘记早期指令 | 关键指令放开头或末尾，必要时重复 |
| 推理时权重不变 | 模型不会记住你 | 记忆、知识都要通过上下文注入 |

可以说，Agent 开发的大部分工程工作，都是在"一个无状态的、按概率续写文本的函数"外面，搭建状态、工具、记忆和校验。

## 常见坑

- **把模型当数据库**：直接问模型某个库的最新版本号、某个 API 的参数，它会给出"看起来对"的答案。事实性信息应该来自工具或文档。
- **以为模型会从对话中学习**：用户纠正过一次，下次新会话模型依然会犯同样的错。需要把纠正写入提示词或记忆。
- **以为上下文越长越好**：把所有资料都塞进去，既贵又可能让关键信息"淹没在中间"。
- **用一次测试结果下结论**：采样带来随机性，改了提示词后跑一次"变好了"不代表真的变好了。参见 [为什么评估是第一优先级](/guide/14-evaluation/why-evals)。

## 小测

**1. 模型生成一段 500 Token 的回答，大致需要经过多少次"预测下一个 Token"？**

::: details 查看答案
大约 500 次。自回归生成每一步产出一个 Token，并把它拼回输入继续预测。这也是输出 Token 通常比输入 Token 更慢、单价更高的原因之一。
:::

**2. 用户说"我上周告诉过你我叫小明"，但模型说不知道。最可能的原因是什么？**

::: details 查看答案
模型推理时权重不变，本身没有跨会话记忆。上周的对话没有被包含在这次请求的上下文里，模型自然无从得知。要实现这种能力，需要应用层把历史信息存储起来，并在请求时注入上下文。
:::

**3. 注意力机制解决的核心问题是什么？**

::: details 查看答案
让模型在处理每个 Token 时，能动态决定上下文中哪些 Token 更相关，并汇总它们的信息。这让模型能处理指代、长距离依赖等问题，并且整段输入可以并行计算。
:::
