# 什么是上下文工程

::: info 学习目标
- 理解上下文工程的定义，以及它和提示词工程的关系
- 认识一次模型调用的上下文由哪些部分组成
- 知道上下文"越多越好"为什么是错的：成本、延迟和注意力稀释
- 掌握写入、选择、压缩、隔离四类策略，并知道本模块后续文章分别对应哪一类
:::

## 从提示词到上下文

[提示词工程](/guide/04-prompt/basics) 关注的是"怎么写好一段指令"。做聊天机器人时这基本够用：系统提示词写好，用户问一句答一句。

到了 Agent 场景，情况变了。一个 Agent 跑 20 步，每一步发给模型的内容都不一样：系统提示词、十几个工具的定义、用户最初的需求、前面每一步的工具调用和结果、从知识库检索到的文档、长期记忆里的用户偏好……这些加起来很容易达到几万甚至几十万 Token。提示词只是其中很小的一部分。

上下文工程（Context Engineering）就是在每一次模型调用前，决定上下文窗口里放什么、怎么放、放多少的工程实践。一句话概括：在有限的窗口里，给模型恰好足够完成下一步的信息。

| 维度 | 提示词工程 | 上下文工程 |
| --- | --- | --- |
| 关注对象 | 指令怎么写 | 窗口里的全部内容 |
| 时间尺度 | 一次调用 | 多轮、多步、跨会话 |
| 主要手段 | 措辞、结构、示例 | 检索、裁剪、摘要、缓存、记忆、子 Agent |
| 典型问题 | 模型没理解意图 | 信息缺失、信息过载、信息过期、成本过高 |
| 关系 | 上下文工程的一个子集 | 包含提示词工程 |

## 上下文由什么组成

以一个处于第 8 步的客服 Agent 为例，一次调用的上下文大致是这样的：

```text
┌─ context window ──────────────────────────────────────┐
│ [1] system prompt        role, rules, output format    │  stable
│ [2] tool definitions     12 tools, JSON Schema         │  stable
│ [3] long-term memory     user profile, preferences     │  per user
│ [4] retrieved docs       top-5 chunks from RAG         │  per step
│ [5] history              user / assistant turns        │  growing
│ [6] tool calls/results   7 steps of observations       │  growing fast
│ [7] current input        the latest user message       │  per step
└────────────────────────────────────────────────────────┘
```

不同部分的特点差异很大：

- [1][2] 几乎不变，适合放在最前面并利用 [Prompt Caching](/guide/07-context-engineering/prompt-caching)。
- [3][4] 每次都要"选"：选哪些记忆、检索哪些文档，选错了就是噪音，见 [RAG 全景](/guide/09-rag/overview) 和 [记忆读写策略与方案对比](/guide/08-memory/memory-strategy)。
- [5][6] 随步数不断增长，而且往往是窗口最大的消耗者。一次网页抓取、一次数据库查询就可能返回几千 Token。这是 [上下文窗口管理](/guide/07-context-engineering/window-management) 和 [压缩与摘要](/guide/07-context-engineering/compression) 主要处理的对象。

## 为什么不能把所有东西都塞进去

模型的窗口越来越大，很自然的想法是"全放进去，让模型自己挑"。这在实践中有三个问题。

成本和延迟。Agent 每一步都会重发整个上下文。上下文翻倍，每一步的输入成本和首 Token 延迟都随之上升，而步数一多，总成本近似按步数的平方增长。

注意力稀释。窗口能装下，不代表模型能用好。研究发现，相关信息放在长上下文中间位置时，模型的利用效果明显低于放在开头或结尾（"Lost in the Middle"）。无关内容越多，模型越容易被带偏，这种随上下文变长而出现的质量下降有时被称为"上下文腐化"（context rot）。

错误累积。上下文里的内容会被模型当作事实：

| 问题 | 表现 | 例子 |
| --- | --- | --- |
| 污染 | 早期的错误信息被后续步骤反复引用 | 第 2 步的幻觉结论，第 10 步还在当作依据 |
| 干扰 | 大量无关内容让模型偏离当前任务 | 一份 5000 字的日志里只有一行有用 |
| 混淆 | 相似信息太多，模型选错 | 30 个功能相近的工具，调用了错误的那个 |
| 冲突 | 上下文中的信息互相矛盾 | 旧版文档和新版文档同时被检索出来 |

所以上下文工程的目标不是"最多"，而是"信噪比最高"。

## 四类基本策略

业界对上下文工程的手段有不少归纳方式，一种常见的划分是四类：写入（Write）、选择（Select）、压缩（Compress）、隔离（Isolate）。

| 策略 | 核心思想 | 典型手段 | 本站相关文章 |
| --- | --- | --- | --- |
| 写入 | 把信息存到窗口之外，需要时再取 | 草稿本 / 待办文件、长期记忆、把大结果存文件只返回路径 | [长期记忆与用户画像](/guide/08-memory/long-term) |
| 选择 | 只把和当前步骤相关的内容放进来 | RAG 检索、记忆召回、按任务动态挑选工具 | [混合检索与重排](/guide/09-rag/hybrid-rerank) |
| 压缩 | 用更少的 Token 表达同样的信息 | 截断工具结果、裁剪旧消息、对历史做摘要 | [上下文窗口管理](/guide/07-context-engineering/window-management)、[压缩与摘要](/guide/07-context-engineering/compression) |
| 隔离 | 把子任务放进独立的上下文 | 子 Agent、沙箱执行环境、分离的状态字段 | [状态共享与通信](/guide/12-multi-agent/state-sharing) |

几个具体例子：

- 写入：[Coding Agent](/guide/13-coding-agent/coding-agents) 常常维护一个待办清单文件，每完成一项就更新它。即使历史被压缩，计划依然完整保存在文件里，随时可以读回来。
- 选择：一个有 50 个工具的 Agent，先根据用户问题检索出最相关的 8 个工具再交给模型，比把 50 个全部塞进去更准确，也更省 Token。
- 压缩：工具返回一个 2 万行的日志，只保留错误行和前后几行；对话超过 30 轮时，把前 20 轮总结成一段摘要。
- 隔离：主 Agent 让一个子 Agent 去"阅读这 10 篇文档并总结要点"。子 Agent 消耗了 10 万 Token 的上下文，返回给主 Agent 的只有 1000 Token 的结论。

此外，提示词缓存不减少 Token 数量，但能显著降低重复前缀的成本和延迟。它对上下文的"排列顺序"有要求，因此也是上下文工程的一部分，见 [Prompt Caching](/guide/07-context-engineering/prompt-caching)。

## 一份上下文设计清单

设计或排查一个 Agent 时，可以逐项检查：

1. 稳定的内容（系统提示词、工具定义）是否放在最前面，且每次调用都保持字节级一致？
2. 每个工具的返回结果有没有长度上限？超长时是截断、摘要，还是存到外部只返回引用？
3. 历史消息超出预算时，按什么规则裁剪？会不会把 `tool_calls` 和对应的 `tool` 消息拆散？
4. 用户最初的目标和关键约束，在长任务后期是否仍然清晰可见？
5. 检索到的文档和记忆，是否有相关性阈值？不相关时是否宁可不放？
6. 能不能把一个"吃上下文"的子任务交给子 Agent，只取回结论？
7. 有没有记录每一步各部分的 Token 占比，便于定位到底是谁占满了窗口？

最后一条往往最先被忽略。很多"模型变笨了"的问题，打开 [轨迹](/guide/14-evaluation/observability) 一看，是某个工具返回了几万 Token 的原始 HTML。

## 常见坑

- 只盯着提示词措辞。花大量时间打磨系统提示词，却放任工具结果把窗口塞满，真正影响效果的是后者。
- 窗口够大就不管。窗口上限只是硬约束，远在达到上限之前，成本、延迟和质量就已经开始恶化。
- 动态内容放在最前面。把当前时间、用户 ID 写在系统提示词开头，导致每次请求的前缀都不同，缓存完全失效。
- 压缩时丢掉关键约束。摘要把"预算不超过 5000 元"这类硬约束概括没了，后续步骤开始违反用户要求。
- 检索结果来者不拒。相关性很低的文档也放进来，反而误导模型，参见 [RAG 评估](/guide/09-rag/rag-eval)。

## 小测

1. 上下文工程和提示词工程是什么关系？

::: details 查看答案
提示词工程是上下文工程的一部分。提示词工程关注单条指令怎么写；上下文工程关注每次模型调用时窗口里的全部内容，包括系统提示词、工具定义、历史、工具结果、检索文档、记忆等，以及它们在多步、多轮中如何选择、裁剪和组织。
:::

2. 模型的上下文窗口已经很大了，为什么还要主动控制上下文长度？

::: details 查看答案
三个原因：一是成本和延迟，Agent 每一步都会重发完整上下文，长度直接决定每一步的费用和响应速度；二是注意力稀释，无关内容越多，模型越难利用关键信息，放在中间的信息尤其容易被忽略；三是错误累积，早期的错误或过期信息留在上下文里，会被后续步骤当作事实反复引用。
:::

3. "主 Agent 把阅读 10 篇长文档的任务交给子 Agent，只接收总结"属于哪类策略？它的代价是什么？

::: details 查看答案
属于隔离。好处是主 Agent 的上下文保持精简。代价是信息损失和额外开销：子 Agent 的总结可能漏掉主 Agent 后来才发现需要的细节，而且多一个 Agent 意味着更多调用和协调成本，见 [多 Agent 的坑与成本控制](/guide/12-multi-agent/pitfalls)。
:::
