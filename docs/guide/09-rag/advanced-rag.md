# GraphRAG 与 Agentic RAG

::: info 学习目标
- 认识朴素 RAG 处理不好的几类问题：全局性问题、多跳问题、模糊问题
- 理解 GraphRAG 的索引流程和"本地 / 全局"两种查询模式
- 理解 Agentic RAG：把检索变成工具，让 Agent 决定何时检索、检索什么、是否够了
- 知道查询改写、HyDE、Self-RAG、CRAG 等常见增强手段的思路
:::

本文以概念和架构为主，不提供三语言代码。Agent 循环的实现见 [不用框架手写 Agent](/guide/06-agent-loop/handwritten-agent)，把其中的工具换成本模块的检索函数即可。

## 朴素 RAG 的边界

前面几篇搭起来的是"朴素 RAG"（Naive RAG）：**问题 → 检索一次 → 拼 prompt → 生成**。它对"答案就在某一两段里"的问题很有效，但面对下面三类问题会力不从心：

| 问题类型 | 例子 | 朴素 RAG 为什么不行 |
| --- | --- | --- |
| 全局性问题 | "这 500 份客户反馈里，最主要的几类抱怨是什么？" | 答案分散在全部文档中，Top-5 片段只能看到局部 |
| 多跳问题 | "负责 A 项目的人，他所在部门的报销审批人是谁？" | 需要先查出 A 项目负责人，再用结果去查下一步，一次检索拿不全 |
| 模糊或复合问题 | "对比一下我们两个产品线今年的退货政策" | 需要拆成多个子问题分别检索 |

两条主要的演进路线分别解决这些问题：**GraphRAG** 改进索引结构，**Agentic RAG** 改进检索流程。

## GraphRAG：用图谱组织知识

GraphRAG 这个名字最广为人知的来源是微软研究院 2024 年的论文和同名开源项目。它的核心想法是：**在索引阶段就用 LLM 把文档"读一遍"，抽取出实体和关系构成知识图谱，再对图谱做社区划分并为每个社区预先生成摘要**。

```text
━━━━━━━━━━━━━━━━━━━━━━━━━━ 索引阶段（离线，LLM 调用量大）━━━━━━━━━━━━━━━━━━━━━━━━━━
 文档 ──► 切块 ──► LLM 抽取实体与关系 ──► 知识图谱
                     "张三" ─负责→ "A项目"      │
                     "张三" ─属于→ "研发部"     ▼
                                       社区发现（把联系紧密的节点聚成社区，可分多层）
                                               │
                                               ▼
                                     LLM 为每个社区生成摘要报告

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 查询阶段 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 本地查询（Local）：问题涉及具体实体 → 找到相关实体 → 沿关系扩展邻居 → 带上原文片段回答
 全局查询（Global）：问题是全局性的 → 把各社区摘要分别交给 LLM 生成局部答案 → 再汇总
```

**它擅长的**：

- **全局性问题**：社区摘要相当于对整个语料做了预先的"分层总结"，回答"主要主题有哪些"这类问题时不再受 Top-K 的限制。
- **关系与多跳**：实体之间的关系显式存在于图中，"A 项目负责人所在的部门"可以沿边遍历得到。

**它的代价**：

- **索引成本高**：每个文本块都要经过 LLM 抽取，大语料的建索引费用可能是朴素 RAG 的很多倍。
- **更新麻烦**：新增文档可能改变社区结构，增量更新比向量索引复杂得多。
- **抽取质量决定上限**：实体消歧（"张总"和"张三"是不是同一个人）、关系抽取出错，都会直接污染图谱。

因此，GraphRAG 更适合**语料相对稳定、全局性问题多、预算充足**的场景，例如研究报告分析、调查访谈汇总、情报分析。对于常规的 FAQ 和制度问答，朴素 RAG + 混合检索通常已经足够，性价比也更高。

社区里也出现了一些更轻量的变体，例如 LightRAG，尝试在保留图结构优势的同时降低索引和更新成本。此外，如果企业已经有结构化的知识图谱（比如存在 Neo4j 中），也可以让 LLM 生成图查询语句（如 Cypher）来检索，这是另一种"图 + RAG"的形态，此时要像对待 SQL 一样限制权限，只允许只读查询。

## Agentic RAG：让 Agent 驱动检索

朴素 RAG 的检索是**固定流程**：不管什么问题，都检索一次、取 Top-K。Agentic RAG 把检索变成 Agent 可以调用的**工具**，由模型在循环中决定：

- **要不要检索**：打招呼、闲聊、简单计算不需要查资料；
- **检索什么**：把用户的口语化问题改写成更好的查询，或拆成多个子查询；
- **够不够**：看完检索结果，判断信息是否充分，不够就换个关键词再查，或者查另一个知识库；
- **怎么回答**：综合多次检索结果，给出带引用的答案。

```text
 用户问题："负责 A 项目的人，他所在部门的报销审批人是谁？"
     │
     ▼
 ┌─────────── Agent 循环（ReAct）────────────┐
 │ 思考：先查 A 项目负责人                      │
 │ 行动：search_kb("A 项目 负责人")             │──► 结果：张三负责 A 项目
 │ 思考：再查张三所在部门                        │
 │ 行动：search_kb("张三 所属部门")             │──► 结果：张三属于研发部
 │ 思考：再查研发部的报销审批人                  │
 │ 行动：search_kb("研发部 报销 审批人")         │──► 结果：研发部报销由李四审批
 │ 思考：信息已足够                             │
 └──────────────────────────────────────────┘
     │
     ▼
 回答：李四。依据：[文档1][文档2][文档3]
```

检索工具的定义和普通的 Tool Calling 没有区别（见 [工具调用原理](/guide/05-tool-calling/concept)），关键在于描述要写清楚**知识库里有什么**，让模型知道什么时候该用它：

```json
{
  "type": "function",
  "function": {
    "name": "search_kb",
    "description": "检索公司内部知识库，包含人事制度、财务报销制度、组织架构和项目信息。返回最相关的若干片段及其来源。问题涉及公司内部信息时调用；一次查询只问一件事。",
    "parameters": {
      "type": "object",
      "properties": {
        "query": { "type": "string", "description": "检索语句，使用关键词或完整的陈述句，不要包含代词" },
        "category": { "type": "string", "enum": ["hr", "finance", "org", "project"], "description": "可选，限定资料类别" },
        "top_k": { "type": "integer", "minimum": 1, "maximum": 10, "default": 5 }
      },
      "required": ["query"]
    }
  }
}
```

工具实现内部，就是前面几篇的混合检索 + 重排。权限过滤应该在工具内部根据**当前登录用户**强制执行，而不是作为参数交给模型决定。

### 朴素 RAG vs Agentic RAG

| | 朴素 RAG | Agentic RAG |
| --- | --- | --- |
| 流程 | 固定：检索一次再生成 | 动态：由模型决定检索次数和内容 |
| 延迟 | 低，可预测 | 高，多轮 LLM 调用 |
| 成本 | 低 | 高，每一步都消耗 Token |
| 多跳 / 复合问题 | 弱 | 强 |
| 可控性与可测试性 | 高 | 较低，需要步数和预算限制 |
| 适合 | FAQ、制度问答、文档搜索 | 研究助手、复杂分析、多知识源 |

实践中常见的折中是：**默认走朴素 RAG 的快速路径，识别到复杂问题时再进入 Agent 模式**。无论哪种，都要设置最大步数和预算，参见 [终止条件、步数与预算控制](/guide/06-agent-loop/stop-budget)。

## 常见增强手段

这些手段既可以嵌进固定流程，也可以作为 Agent 的能力。它们的共同点是：**在检索前后多加一步 LLM 处理**。

| 手段 | 做法 | 解决的问题 |
| --- | --- | --- |
| 查询改写 | 结合对话历史，把"那第二种呢？"改写成完整、独立的问题 | 多轮对话中的指代和省略 |
| 多查询（Multi-Query） | 让 LLM 把问题改写成 3~5 种表述，分别检索后用 RRF 融合 | 单一表述召回不全 |
| 问题分解 | 把复合问题拆成多个子问题，逐个检索 | 对比类、复合类问题 |
| HyDE | 先让 LLM 写一个"假设答案"，用它的 Embedding 去检索 | 问题短、与文档表述差异大 |
| Step-back | 先把具体问题抽象成更一般的问题，检索背景知识 | 需要原理性背景的问题 |
| Self-RAG | 训练模型在生成过程中自行判断是否需要检索、检索结果是否相关、回答是否有依据 | 不必要的检索和无依据的生成 |
| CRAG（Corrective RAG） | 用评估器判断检索结果质量，质量差时改写查询或转向其他来源（如网页搜索） | 检索结果质量差时的兜底 |

Self-RAG 原论文需要专门训练模型，不过它"检索后自我评估"的思想很容易用提示词近似实现：在 Agent 循环中加一步，让模型判断"这些资料能否回答问题"，不能就再检索或如实说不知道。

## 怎么选

```text
 问题的答案通常在一两段文字里？
   ├─ 是 → 朴素 RAG + 混合检索 + 重排（先把这个做好）
   └─ 否 → 是"全局总结"类问题？
            ├─ 是 → GraphRAG（或预先离线生成的分层摘要）
            └─ 否 → 多跳 / 复合 / 多知识源？
                     └─ 是 → Agentic RAG（加步数与预算限制）
```

最重要的一条建议：**先把朴素 RAG 做到位，再上高级方案**。很多团队上了 GraphRAG 和多 Agent 后发现效果没提升，根本原因是切分和检索本身就有问题。高级方案会放大基础能力，也会放大基础问题。

## 常见坑

- **用高级方案掩盖基础问题**：解析错乱、切分不合理时，任何高级架构都救不回来。
- **低估 GraphRAG 的索引成本**：先用一小部分语料试算抽取的 Token 消耗，再决定是否全量上线。
- **Agent 无限检索**：模型总觉得"信息还不够"，反复换词检索。设置最大检索次数，并在提示词里说明何时应该停止。
- **把权限交给模型**：检索工具的 `category` 之类参数只是用于缩小范围，用户能访问哪些文档必须由后端按身份强制过滤。
- **检索结果中的注入**：Agent 会根据检索结果决定下一步行动，文档中植入的恶意指令可能诱导它调用其他工具。检索内容一律视为数据，高风险工具需要人工确认，见 [Prompt 注入与防护](/guide/15-production/prompt-injection)。

## 小测

**1.** "总结过去一年所有客户投诉的主要类型"，为什么朴素 RAG 难以回答？GraphRAG 是怎么处理的？

::: details 查看答案
答案分散在全部投诉文档中，朴素 RAG 只检索 Top-K 片段，只能看到局部样本，无法做全局归纳。GraphRAG 在索引阶段就对图谱做了社区划分，并为每个社区生成摘要；全局查询时，基于各社区摘要分别生成局部答案，再汇总成最终答案。
:::

**2.** Agentic RAG 相对朴素 RAG 的主要代价是什么？如何缓解？

::: details 查看答案
代价是延迟更高、成本更高、行为更难预测和测试。缓解方法：简单问题走固定的快速路径，复杂问题才进入 Agent 模式；限制最大步数和 Token 预算；记录完整轨迹用于评估和调试。
:::

**3.** 多轮对话中，用户问"那第二种方案的成本呢？"，直接拿这句话检索会有什么问题？

::: details 查看答案
这句话缺少主语和上下文，"第二种方案"指什么只有结合对话历史才知道，直接检索几乎召回不到相关内容。应该先用 LLM 结合历史把它改写成一个独立完整的问题（如"XX 项目第二种部署方案的成本是多少"），再去检索。
:::
