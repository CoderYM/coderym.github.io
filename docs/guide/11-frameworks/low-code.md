# 低代码平台：Dify 与 Coze

::: info 学习目标
- 了解低代码 Agent 平台提供了哪些能力，和代码框架是什么关系
- 对比 Dify 与 Coze 的定位、部署方式和适用场景
- 掌握"低代码搭原型 + API 集成到业务系统"的常见用法
- 判断一个需求该用低代码还是写代码，以及何时迁移
:::

本文是概念与选型文章，不包含代码。平台功能更新很快，具体功能以官方文档为准。

## 低代码平台在做什么

回顾前面的模块：调用模型、写提示词、定义工具、做 RAG、编排流程、管理会话。低代码平台把这些能力做成了可视化的积木：

```text
┌──────────────────────── 低代码 Agent 平台 ─────────────────────────┐
│                                                                    │
│  模型接入      提示词编辑      知识库（RAG）     插件 / 工具           │
│  (多厂商切换)  (变量、调试)    (上传文档即可)    (HTTP API、MCP 等)     │
│                                                                    │
│  ┌─────────── 可视化工作流画布 ───────────┐                          │
│  │ 开始 → LLM → 条件分支 → 工具 → 代码 → 结束 │                       │
│  └────────────────────────────────────────┘                        │
│                                                                    │
│  发布：Web 应用 / API / 嵌入网页 / 接入 IM 渠道   运营：日志、标注、统计  │
└────────────────────────────────────────────────────────────────────┘
```

本质上，它们是把 [Agent、Chatbot 与 Workflow 的区别](/guide/00-intro/agent-vs-workflow) 里讲的两类应用，以产品化的方式交付：

- **Agent 模式**：给定提示词、工具和知识库，由模型自主决定调用什么，对应 [ReAct](/guide/06-agent-loop/react) 循环；
- **工作流模式**：在画布上拖出确定的步骤和分支，模型只是其中的节点，适合流程固定、需要稳定输出的业务。

## Dify 与 Coze

| 维度 | Dify | Coze（扣子） |
|------|------|-------------|
| 出品方 | LangGenius（开源社区项目） | 字节跳动 |
| 开源与部署 | 开源，可用 Docker 自部署，也有云服务 | 以云服务为主；2025 年开源了 Coze Studio 和 Coze Loop，可自部署 |
| 模型 | 支持大量厂商与本地模型（如通过 Ollama），自行配置 Key | 云版深度集成豆包等模型；开源版可自行接入模型 |
| 核心能力 | Chatflow、Workflow、Agent、知识库、插件、MCP | Agent（智能体）、工作流、知识库、插件、多渠道发布 |
| 发布渠道 | Web 应用、API、嵌入网页 | 豆包、飞书、微信等渠道，以及 API / SDK |
| 典型用户 | 需要私有化部署的企业、开发团队 | 面向个人与业务人员的快速搭建，和字节生态结合紧密 |
| 许可 | 基于 Apache 2.0 并附加条件（如多租户、商标方面的限制），商用前需阅读许可 | 开源部分采用 Apache 2.0；云服务按平台条款 |

简单理解：**数据要留在自己机房、需要深度定制，倾向 Dify；想快速做出能在飞书、豆包等渠道使用的 Bot，倾向 Coze**。同类平台还有 n8n（偏通用自动化）、FastGPT（偏知识库问答）、阿里云百炼等，思路相近。

## 典型用法

### 1. 快速验证想法

产品经理或业务专家可以在一个下午搭出"上传产品手册 → 客服问答"的原型，直接拿真实问题去测试。如果效果不行，问题往往在知识库质量或需求本身，而不是代码，这时候还没写一行代码，试错成本最低。

### 2. 作为后端能力被业务系统调用

Dify 和 Coze 发布的应用都可以通过 HTTP API 调用。常见架构是：

```text
  业务系统（Java / Go / Python）
        │  HTTP API（带 API Key）
        ▼
  低代码平台上的工作流 / Agent  ──▶ 知识库、模型、插件
```

业务系统负责鉴权、用户体系和数据落库，平台负责"AI 那一段"。提示词和流程的调整由运营在平台上完成，不需要业务系统发版。

### 3. 和代码混合使用

- 平台工作流中的 "代码" 节点可以写 Python / JavaScript 片段处理数据；
- 复杂的工具用代码实现成 HTTP API 或 [MCP Server](/guide/10-mcp/mcp-server)，再注册为平台插件；
- 平台只负责编排与运营，核心逻辑留在你可测试、可版本管理的代码里。

## 低代码还是写代码

| 考量 | 倾向低代码 | 倾向写代码 |
|------|-----------|-----------|
| 需求阶段 | 探索期、需求不清楚 | 需求稳定、准备规模化 |
| 维护者 | 业务人员、运营参与调整 | 研发团队维护 |
| 流程复杂度 | 线性流程、少量分支 | 复杂状态、长时间运行、人工审批、多 Agent 协作 |
| 测试与发布 | 可接受平台内的手工测试 | 需要单元测试、[回归测试](/guide/14-evaluation/regression)、代码评审、灰度发布 |
| 性能与成本 | 调用量不大 | 高并发、需要精细控制 Token 与延迟 |
| 集成深度 | 调几个 HTTP 接口 | 深度嵌入现有系统、复杂权限模型 |

一个常见的演进路径：**低代码搭原型 → 验证价值 → 把高频、复杂、对稳定性要求高的部分逐步迁移到代码**，平台上保留运营频繁调整的部分。

## 迁移时机的信号

出现以下情况时，就该认真考虑迁移到代码框架：

- 画布上的节点多到一屏放不下，没人能说清整个流程；
- 需要做版本对比、回滚和自动化评估，而平台的版本管理满足不了；
- 每次改动都担心影响其他场景，但没有办法做回归测试；
- 需要平台不支持的能力，例如精细的上下文管理（见 [什么是上下文工程](/guide/07-context-engineering/overview)）、自定义的重试与降级；
- 调用量增长后，平台成本或性能成为瓶颈。

## 常见坑

- **把平台当成"不需要懂原理"**：知识库效果差、Agent 乱调用工具时，排查方法和代码开发完全一样：看检索结果、看提示词、看工具描述。前面模块的知识在这里同样必要。
- **API Key 暴露在前端**：平台应用的 API Key 拥有调用权限和费用，应只在后端使用，不要写进网页或 App 代码。
- **忽视数据合规**：使用云服务时，上传的文档和对话数据存储在平台方。涉及客户数据、内部资料时，先确认合规要求，必要时选择私有化部署。
- **没有评估集**：在平台上改了提示词"感觉更好了"就发布，结果其他问题变差。准备一组固定的测试问题，每次改动后都跑一遍，参考 [评估集与指标设计](/guide/14-evaluation/eval-design)。
- **忽略许可证条款**：开源不等于可以随意商用或改造成 SaaS 对外售卖，自部署商用前阅读对应版本的许可证。

## 小测

1. 一家医疗机构希望基于内部诊疗规范做一个问答助手，数据不能出院区，Dify 和 Coze 云版应该选哪个？为什么？

::: details 查看答案
优先选择可私有化部署的方案，例如自部署 Dify（或自部署 Coze 开源版），并接入本地或私有云部署的模型，确保文档和对话数据不离开内网。Coze 云版的数据存储在平台方，不满足数据不出院区的要求。
:::

2. 什么情况下应该把一个 Dify 工作流迁移为代码实现？列举至少两个信号。

::: details 查看答案
例如：流程复杂到难以理解和维护；需要自动化回归测试、代码评审和灰度发布；需要平台不支持的能力（复杂状态、人工审批、自定义重试降级）；调用量增长后性能或成本成为瓶颈。
:::

3. 为什么说"低代码平台 + 自研 MCP Server / HTTP API"是一种不错的混合方案？

::: details 查看答案
核心业务逻辑和对外系统的访问写成代码，可以测试、做权限控制和版本管理；平台只负责编排和提示词，运营可以灵活调整。两者各取所长，以后迁移到代码框架时，工具部分也能直接复用。
:::
