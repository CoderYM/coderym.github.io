# 为什么需要多 Agent

::: info 学习目标
- 说清楚"多 Agent 系统"到底指什么，以及它和"一个 Agent 调很多工具"的区别
- 理解为什么大多数场景下单 Agent 更好：更便宜、更好调试、上下文不丢失
- 掌握多 Agent 真正划算的三类场景：可并行的研究、上下文隔离、专业分工
- 学会用一张检查清单判断"我该不该拆"
:::

## 先统一概念

本站说的 **多 Agent 系统（Multi-Agent System）**，指的是由多个各自拥有独立上下文、独立系统提示词、通常也有独立工具集的 LLM 循环协作完成一个任务。每个 Agent 都是一个完整的 [Agent 循环](/guide/06-agent-loop/react)：思考 → 调用工具 → 观察 → 再思考。

它和下面两种东西不同：

| 形态 | 上下文 | 典型例子 |
| --- | --- | --- |
| 单 Agent + 多工具 | 一份上下文，模型自己决定调哪个工具 | 一个客服 Agent 能查订单、查物流、退款 |
| Workflow（固定流程） | 每一步可能调 LLM，但流程由代码写死 | "翻译 → 校对 → 排版"三步管道 |
| 多 Agent | 多份互相隔离的上下文，Agent 之间传递消息或结果 | 主 Agent 派 5 个子 Agent 并行调研 5 个方向 |

关键区别在于 **上下文是否隔离**。单 Agent 里，所有工具结果都堆进同一个消息列表；多 Agent 里，子 Agent 读了 50 个网页，只把 500 字的结论交回去，主 Agent 永远看不到那 50 个网页的原文。这既是多 Agent 最大的优点，也是它最大的风险来源。

```text
单 Agent：                         多 Agent（主从）：

┌──────────────────────┐           ┌──────────────┐
│ 一个上下文窗口        │           │ 主 Agent      │  只看到各子任务的摘要
│  system prompt       │           └──┬────┬────┬─┘
│  user 任务            │              │    │    │   派发子任务
│  tool 结果 1          │           ┌──▼┐ ┌─▼─┐ ┌▼──┐
│  tool 结果 2          │           │子A│ │子B│ │子C│  各自独立上下文
│  ...越来越长          │           └───┘ └───┘ └───┘  各自读大量资料
└──────────────────────┘
```

## 大多数情况下，单 Agent 更好

这一点值得先说清楚：**绝大多数业务场景，一个设计良好的单 Agent 就够了，而且更好。** 理由很具体：

1. **信息不丢失。** 单 Agent 的每一次决策都基于完整历史。多 Agent 之间只传摘要，摘要必然有损。子 Agent A 发现的一个关键约束，如果没写进它交回的结论，子 Agent B 就不知道，最后两个人的产出互相矛盾。
2. **成本更低。** 每个 Agent 都要重复读系统提示词、任务描述和共享背景。多 Agent 系统的 Token 消耗常常是单 Agent 的数倍，这是公开工程经验里反复出现的结论。
3. **更好调试。** 单 Agent 出错，你看一条轨迹就能定位。多 Agent 出错，你要在多条并发轨迹之间对时间线，判断是"主 Agent 拆错了任务"还是"子 Agent 执行错了"还是"汇总时丢了信息"。
4. **决策一致。** 写代码、改文档这类任务，前后决策高度耦合。拆给两个 Agent 分别写前端和后端，接口约定很容易对不上。

很多人想拆多 Agent，其实真正的问题是别的：

| 你以为的问题 | 真正的原因 | 更好的解法 |
| --- | --- | --- |
| "一个 Agent 管不了这么多工具" | 工具描述写得差、工具太多太像 | [工具设计原则](/guide/05-tool-calling/tool-design)，合并或分组工具 |
| "上下文太长，模型变笨" | 工具结果原样塞回上下文 | [上下文窗口管理](/guide/07-context-engineering/window-management)、[压缩与摘要](/guide/07-context-engineering/compression) |
| "需要多个角色把关" | 缺少检查步骤 | 加一步 [Reflection](/guide/06-agent-loop/reflection) 或固定的校验 Workflow |
| "流程很长，容易跑偏" | 缺少计划 | [Plan-and-Execute](/guide/06-agent-loop/plan-execute) |

先试这些，再考虑拆分。

## 多 Agent 真正划算的三类场景

### 1. 可并行的广度型研究

典型任务："调研 2020 年以来所有主流开源向量数据库，对比它们的索引类型、分布式能力和许可证。"

这类任务的特点是 **子任务之间几乎独立**：调研 Milvus 不需要知道 Qdrant 的结论。拆成多个子 Agent 并行跑，有两个收益：

- **墙钟时间缩短**：5 个方向并行，总耗时接近最慢的那一个，而不是 5 个相加。
- **总探索量变大**：每个子 Agent 都有一整个上下文窗口可以用来读资料，系统整体能"读"的信息量是单 Agent 的数倍。

Anthropic 公开分享过他们的多 Agent 研究系统，结论正是：在广度优先、可并行的研究类问题上，多 Agent 明显好于单 Agent，代价是 Token 消耗大幅上升。所以它适合 **任务价值高到能覆盖额外成本** 的场景。

### 2. 上下文隔离

有些子任务会产生大量"中间垃圾"：搜索结果、网页原文、日志、测试输出。主任务只需要结论。

例如一个代码 Agent 需要"在整个仓库里找出所有调用了已废弃 API 的地方"。如果主 Agent 自己做，几十次搜索结果会把上下文塞满，后面真正改代码时反而记不住需求。交给一个子 Agent 去搜，只返回一个文件和行号列表，主 Agent 的上下文就保持干净。

Claude Code 等编码工具里的"子 Agent"（subagent）主要就是这个用途：**用一次性的上下文去做脏活，只把结论带回来。**

### 3. 专业分工与权限隔离

当不同子任务需要 **完全不同的系统提示词、工具集或权限** 时，拆开更清晰也更安全：

- 一个"数据库 Agent"只有只读 SQL 工具，一个"邮件 Agent"只有发送草稿的工具，互相不能越权。
- 一个审查 Agent 不看实现者的推理过程，只看最终代码，审查更独立（类似人类的 code review 不该被作者的思路带偏）。
- 不同 Agent 可以用不同的模型：便宜的小模型做检索和分类，强模型做规划和汇总。

## 一张决策清单

在动手拆分之前，逐条回答：

```text
[ ] 单 Agent + 好的工具设计 + 上下文管理，我已经认真试过了吗？
[ ] 子任务之间真的独立吗？（需要频繁互相同步的任务不适合拆）
[ ] 子任务会产生大量主任务不需要的中间信息吗？
[ ] 不同子任务需要不同的权限、工具或模型吗？
[ ] 任务价值能覆盖数倍的 Token 成本吗？
[ ] 我有能力追踪多条并发轨迹吗？（见 [评估与可观测性] 模块）
```

前两条有一条是"否"，就先别拆。后面四条至少满足一条，拆分才有意义。可观测性部分见 [轨迹追踪与可观测性](/guide/14-evaluation/observability)。

## 演进路径

推荐的演进顺序是从简单到复杂，每一步都用 [评估集](/guide/14-evaluation/eval-design) 证明收益后再往下走：

```text
单次 LLM 调用
   └─▶ 固定 Workflow（代码编排几次调用）
         └─▶ 单 Agent（模型自主调用工具）
               └─▶ 单 Agent + 子 Agent（仅用于上下文隔离的脏活）
                     └─▶ 主从多 Agent（并行研究）
                           └─▶ 更复杂的拓扑（交接、辩论、网状）
```

大部分生产系统停在第三或第四层。具体的编排方式见下一篇 [编排模式：主从、流水线、交接、辩论](/guide/12-multi-agent/patterns)。

## 常见坑

- **为了"看起来高级"而拆分。** 给 Agent 起"产品经理""架构师""程序员"这样的角色名，并不会让它们更聪明，只会让信息在角色之间多传几手、多丢几次。
- **拆分耦合的任务。** 让两个 Agent 分别写同一个功能的前后端，最常见的结果是接口不一致。耦合紧的任务交给一个 Agent 按顺序做。
- **没有基线。** 不先测单 Agent 的效果，就无法证明多 Agent 带来了提升，只能确定成本上去了。
- **忽视成本放大。** 每多一个 Agent，系统提示词、共享背景都要重复计费。上线前先估算一次完整任务的 Token 消耗，见 [多 Agent 的坑与成本控制](/guide/12-multi-agent/pitfalls)。

## 小测

1. 多 Agent 与"单 Agent 调用很多工具"最本质的区别是什么？

::: details 查看答案
上下文是否隔离。多 Agent 中每个 Agent 拥有独立的上下文窗口，彼此只通过消息或结果摘要交流；单 Agent 所有信息都在同一个上下文里。隔离带来了并行和"不被中间信息污染"的好处，也带来了信息丢失和协调成本。
:::

2. 下面哪个任务最适合多 Agent？A. 给一个 Python 函数加单元测试；B. 对比 8 家云厂商的 GPU 实例规格和地域覆盖；C. 把一篇中文文章翻译成英文。

::: details 查看答案
B。8 家厂商的调研互相独立，可以并行，每个子任务都需要读大量网页，只需要回传结构化结论。A 和 C 是单一、连贯的任务，单 Agent 或简单 Workflow 即可。
:::

3. 你的 Agent 有 40 个工具，模型经常选错工具。同事建议拆成 4 个专业 Agent，你会先做什么？

::: details 查看答案
先检查工具设计：是否有功能重叠、命名含糊、描述不清的工具，能否合并或按场景动态加载工具子集。工具选择错误通常是工具设计问题，拆分 Agent 会额外引入路由错误和信息丢失。如果优化后仍有明确的权限或领域边界，再考虑拆分。
:::
