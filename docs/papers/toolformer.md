# Toolformer

## 论文信息

- 标题：Toolformer: Language Models Can Teach Themselves to Use Tools
- 作者：Timo Schick、Jane Dwivedi-Yu、Roberto Dessì、Roberta Raileanu、Maria Lomeli、Luke Zettlemoyer、Nicola Cancedda、Thomas Scialom（Meta AI Research 等）
- 年份：2023（NeurIPS 2023）
- 链接：[arXiv:2302.04761](https://arxiv.org/abs/2302.04761)

## 一句话总结

让模型自己在文本中插入候选的 API 调用，只保留"调用结果确实有助于预测后文"的那些，再用这些数据微调模型，模型就学会了自主决定何时、如何使用工具。

## 要解决的问题

大模型在很多任务上能力很强，却在一些"简单"的事情上出错：算术计算、查询最新事实、知道今天是几号、低资源语言翻译。这些恰好是外部工具（计算器、搜索引擎、日历、翻译系统）擅长的。

当时让模型使用工具的方法有两类问题：

- 依赖大量人工标注的工具使用数据，成本高。
- 只针对特定任务设计，模型不能自己判断"这里需不需要用工具"。

作者希望找到一种方法，让模型以自监督的方式学会通用的工具使用能力，同时不损害它原本的语言建模能力。

## 核心方法

API 调用被表示成插在普通文本中的特殊片段，格式类似 `[Calculator(400 / 1400) → 0.29]`。整个数据构造流程分三步：

```text
 普通文本语料
     │
     ▼
 ┌──────────────────────────────────────────────────────────┐
 │ 1. 采样：用少量示例提示模型，在文本中可能需要工具的位置       │
 │    生成候选 API 调用，例如 [QA("谁创立了某公司?")]          │
 └──────────────────────────────────────────────────────────┘
     │
     ▼
 ┌──────────────────────────────────────────────────────────┐
 │ 2. 执行：真正调用工具，拿到返回结果                          │
 └──────────────────────────────────────────────────────────┘
     │
     ▼
 ┌──────────────────────────────────────────────────────────┐
 │ 3. 过滤：比较"插入调用和结果"前后，模型预测后续文本的损失     │
 │    只有损失明显降低（即结果真的有用）的调用才被保留           │
 └──────────────────────────────────────────────────────────┘
     │
     ▼
 带有 API 调用的增强语料 ──▶ 微调原模型 ──▶ Toolformer
```

推理时，模型正常生成文本；当它生成 API 调用的标记时，程序暂停生成、执行工具、把结果插回文本，再让模型继续。

论文使用的工具包括：问答系统、计算器、Wikipedia 搜索、机器翻译和日历。基座模型是一个约 67 亿参数的 GPT-J。

## 关键实验结论

- **小模型配合工具可以在多个零样本任务上超过大得多的模型。** 经过训练的 Toolformer 在事实问答、数学计算、时间相关问题等任务上，表现超过了不使用工具的更大规模模型。
- **模型学会了"按需"调用。** 在需要计算的地方调用计算器，在需要事实的地方调用问答或搜索，在无关的地方不调用。
- **语言建模能力没有明显下降。** 在不允许调用工具时，模型的困惑度与原模型相近。
- **工具使用能力与模型规模有关。** 较小的模型很难从工具中获益，模型达到一定规模后才学会有效利用工具。

## 对 Agent 开发的启发

- **工具调用不是外挂，而是可以被训练进模型的能力。** 今天主流模型原生支持 Tool Calling，背后正是这类研究的延续。作为应用开发者，你通常不需要自己训练，但要理解模型"何时调用工具"是一种学到的判断，会出错。
- **"有用"是选择工具调用的标准。** Toolformer 用"能否降低后文预测损失"来判断调用是否有价值。在 Agent 设计中，对应的问题是：这个工具返回的信息是否真的帮助完成任务？无用的工具调用只会浪费上下文和成本。
- **工具返回要简洁。** 论文中工具结果是被直接插入文本的短片段，这提醒我们工具返回应当精炼、与任务相关，而不是把整个页面塞给模型。
- **把模型不擅长的事交给确定性工具。** 计算、日期、精确查询这类任务，给模型一个工具比在提示词里反复强调"请仔细计算"可靠得多。

## 局限性

- 工具不能链式使用：一个工具的输出不能作为另一个工具的输入，因为每个工具的训练数据是独立生成的。
- 不支持交互式使用：模型不能根据工具返回结果追问或调整调用，比如搜索结果不理想时重新搜索。
- 对提示词措辞敏感，判断是否调用工具时有时不稳定。
- 数据构造需要在大量文本上采样和执行工具，部分工具的有效样本很少，效率不高。
- 没有考虑调用工具的成本，模型不知道某个工具"贵"或"慢"。

这些局限正是后来 [ReAct](/papers/react) 式的交互循环和原生 Tool Calling 接口所弥补的。
