# Tree of Thoughts

## 论文信息

- 标题：Tree of Thoughts: Deliberate Problem Solving with Large Language Models
- 作者：Shunyu Yao、Dian Yu、Jeffrey Zhao、Izhak Shafran、Thomas L. Griffiths、Yuan Cao、Karthik Narasimhan（Princeton University、Google DeepMind）
- 年份：2023（NeurIPS 2023）
- 链接：[arXiv:2305.10601](https://arxiv.org/abs/2305.10601)

## 一句话总结

把推理过程拆成一个个"思维步骤"，在每一步生成多个候选，让模型自己评估哪些候选更有希望，再用广度优先或深度优先搜索探索、剪枝和回溯，解决思维链一条路走到底解决不了的问题。

## 要解决的问题

[Chain-of-Thought](/papers/chain-of-thought) 让模型一步一步推理，但它本质上还是从左到右逐 Token 生成，一旦早期某一步走错，后面就很难纠正。

人类解决难题时并不是这样：我们会考虑几种思路，评估哪种更可行，发现死路后退回来换一种。作者希望让模型也具备这种"有意识的规划和搜索"能力，尤其针对需要探索、前几步决策影响很大的任务。

## 核心方法

ToT 把问题求解建模为在一棵"思维树"上的搜索，需要设计四个部分：

1. **思维分解：** 定义一个"思维步骤"的粒度，比如一个算式、一段写作计划、填一个单词。
2. **思维生成：** 在每个节点，让模型生成若干个候选的下一步。
3. **状态评估：** 让模型给每个候选打分（比如"确定可行 / 可能 / 不可能"），或在多个候选中投票。
4. **搜索算法：** 用 BFS（每层保留最好的若干个）或 DFS（沿最有希望的分支深入，不行就回溯）。

```text
                         问题
                          │
           ┌──────────────┼──────────────┐
           ▼              ▼              ▼
        思路 A          思路 B          思路 C        ◀── 生成多个候选
       评估:可能        评估:确定        评估:不可能     ◀── 模型自评
           │              │              ✗ 剪枝
      ┌────┴────┐     ┌───┴────┐
      ▼         ▼     ▼        ▼
     A1        A2    B1       B2
   不可能     可能   确定     可能
     ✗         │     │
               …     ▼
                    答案  ◀── 找到可行解；若走入死路则回溯到上一层

  对比：Chain-of-Thought 只有一条路径   问题 ──▶ 步骤1 ──▶ 步骤2 ──▶ 答案
```

生成和评估都由同一个大模型通过不同的提示词完成，不需要训练任何额外模型。

## 关键实验结论

论文设计了三个需要规划或搜索的任务：24 点游戏（用四个数字和四则运算得到 24）、创意写作（写出结尾句子给定的连贯段落）、迷你填字游戏。

- **24 点游戏：** 这是提升最明显的任务。标准提示和思维链的成功率很低，ToT 将成功率提升到了大多数题目都能解出的水平。原因是 24 点的早期选择错误后很难挽回，而 ToT 可以评估并剪掉不可能的分支。
- **创意写作：** 人工和模型评估都认为 ToT 生成的文章更连贯，但提升幅度比 24 点小。
- **填字游戏：** 使用 DFS 加回溯后，单词和整题的完成率都明显高于思维链。消融实验显示，去掉剪枝或回溯，效果都会下降。
- **代价：** ToT 需要的模型调用次数和 Token 数远多于思维链。

## 对 Agent 开发的启发

- **"生成多个候选再选择"是通用模式。** 不一定要完整实现树搜索，在关键决策点生成几个方案、让模型或规则评估后再执行，往往就能带来收益。
- **评估器是核心。** ToT 的效果取决于模型能否准确判断"这条路有没有希望"。在 Agent 中，能用确定性规则（测试、校验、计算）评估的地方，尽量不要只依赖模型自评。
- **为任务选择合适的控制流。** 大多数 Agent 任务用 [ReAct](/papers/react) 或 [Plan-and-Execute](/guide/06-agent-loop/plan-execute) 就够了；只有在"早期决策影响大、需要试错"的任务上，搜索类方法才值得它的成本。
- **推理模型在一定程度上内化了这一思路。** 今天的推理模型在内部也会探索和自我修正，很多场景下直接使用推理模型比手写树搜索更简单。

## 局限性

- 成本高：每一步都要生成多个候选并逐个评估，调用次数成倍增长，延迟也高。
- 需要针对任务手工设计思维粒度、评估提示词和搜索策略，通用性有限。
- 评估依赖模型自身判断，模型评估错误会导致剪掉正确分支。
- 实验任务偏向谜题类，在开放的真实任务中效果还需要验证。
- 对于模型本来就擅长的任务，搜索带来的收益很小。
