Agent 到底是什么 ​

学习目标

  • 给出一个能指导工程实践的 Agent 定义，而不是营销口号
  • 理解 Agent 的四个组成部分：模型、工具、循环、环境（含记忆）
  • 能判断一个系统「是不是 Agent」以及「Agent 程度有多高」
  • 建立后续模块的整体地图：每个模块解决 Agent 的哪一块问题

从一次 LLM 调用说起 ​

最简单的大模型应用是这样的：把用户问题发给模型，模型返回一段文字，结束。

text
用户问题 ──▶ LLM ──▶ 回答
1

这类应用能做很多事：翻译、总结、写邮件。但它有两个硬限制：

  1. 只能「说」，不能「做」。模型不知道今天的天气，不能查你的数据库，也不能帮你改代码文件。
  2. 只有一步。模型一次性给出答案，没有机会根据中间结果调整做法。

现在换个问题：「帮我查一下上海明天的天气，如果下雨就把我日历上下午的户外会议改到室内。」一次调用显然不够，你需要：查天气 → 读结果 → 判断 → 查日历 → 修改会议 → 汇报。哪一步做什么、做不做，取决于上一步的结果。

让模型自己决定下一步做什么，并通过工具真正去做，循环直到完成任务，这就是 Agent。

一个可操作的定义 ​

业界对 Agent 的定义很多，本站采用一个偏工程的版本：

Agent 是一个以 LLM 为决策核心、能够调用工具与环境交互、并在循环中根据反馈自主决定下一步行动、直到达成目标的系统。

Anthropic 在《Building effective agents》里给了一个类似的区分：Workflow 是「LLM 和工具按预先写好的代码路径编排」，Agent 是「LLM 动态地主导自己的流程和工具使用」。关键词是谁来决定控制流。

拆开看，一个 Agent 有四个组成部分：

Agent 循环的最小形态 ​

把上面的图写成伪代码，Agent 的核心只有十几行：

text
messages = [system_prompt, user_task]
for step in 1..MAX_STEPS:
    reply = llm(messages, tools=tool_definitions)
    if reply 没有请求调用工具:
        return reply.text            # 模型认为任务完成
    for call in reply.tool_calls:
        result = execute(call.name, call.arguments)   # 真正执行
        messages.append(result)      # 把观察结果喂回模型
return "达到最大步数，停止"

注意几件事：

  • 模型并不执行工具。模型只是输出「我想调用 get_weather，参数是 {"city": "上海"}」这样的结构化请求，真正执行的是你的代码。这也是安全控制的落点。
  • 循环是关键。没有循环，就只是「带工具的单次调用」；有了循环，模型才能根据观察结果修正计划。
  • 必须有终止条件。最大步数、Token 预算、超时，缺一不可，否则一个困惑的模型会一直调用工具烧钱。

这个循环在 06 Agent 循环 里会用 Python / Go / Java 完整实现一遍。

Agent 是一个光谱，不是开关 ​

「这个系统算不算 Agent」常常争论不休。更有用的问法是：模型在多大程度上掌控流程？

层级描述例子
L0 单次调用输入 → 输出，无工具翻译、摘要
L1 增强型 LLM单次调用 + 检索或一次工具调用简单 RAG 问答
L2 Workflow多步骤，但步骤顺序由代码写死「抽取 → 校验 → 生成报告」流水线
L3 单 Agent模型在循环中自主选择工具和步骤编程助手、研究助手
L4 多 Agent多个 Agent 分工协作、互相交接规划 Agent + 执行 Agent + 审查 Agent

层级越高，灵活性越强，但成本、延迟、不可预测性也越高。工程上的原则是：用能解决问题的最低层级。下一篇 Agent、Chatbot 与 Workflow 的区别 会详细讨论如何选择。

为什么是现在 ​

Agent 的思想并不新，强化学习和经典 AI 里早就有「智能体」概念。最近几年它变得可用，主要因为三件事：

  1. 模型推理能力提升：能可靠地理解复杂指令、拆解任务。
  2. 原生 Tool Calling：主流模型 API 都支持结构化的工具调用，不再需要用正则从文本里抠参数。
  3. 长上下文：模型一次能看到更多历史和工具结果，多步任务不容易「失忆」。

但要清醒：Agent 依然会犯错、会幻觉、会在循环里打转。理解这些边界，是 Agent 的能力边界与适用场景 的主题。

常见坑 ​

  • 把「接了大模型的聊天框」叫 Agent。没有工具和循环，它只是 Chatbot。概念不清会导致架构选型错误。
  • 以为模型会「自己执行」工具。工具永远由你的代码执行，权限、超时、参数校验都是你的责任。
  • 一上来就做多 Agent。大多数问题用一个设计良好的单 Agent，甚至一个 Workflow 就能解决。
  • 忽略终止条件。生产环境里没有步数和预算上限的 Agent 是事故隐患。

小测 ​

1. 一个系统先用 LLM 把用户问题分类，然后根据分类结果走三条写死的代码分支之一，最后再用 LLM 生成回复。它是 Agent 吗？

查看答案

按本站定义，它更接近 Workflow（L2）。虽然用了多次 LLM 调用，但控制流由代码预先决定，模型没有在循环中自主选择行动。这并不是缺点，对于路径明确的任务，Workflow 往往更稳定、更便宜。

2. 在 Agent 循环中，模型输出了一个 Tool Call 请求，接下来由谁执行？执行结果去哪里？

查看答案

由宿主程序（你的代码）解析请求、校验参数并执行对应函数。执行结果作为一条新消息追加到对话上下文中，在下一轮发给模型，模型据此决定继续调用工具还是给出最终答案。

3. 为什么说 Agent 必须有终止条件？列出至少两种。

查看答案

模型可能误判任务未完成，或在错误路径上反复尝试，导致无限循环、成本失控。常见终止条件：最大步数、Token 或费用预算、总超时时间、连续错误次数上限，以及需要人工确认的高风险操作。
