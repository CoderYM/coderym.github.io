记忆读写策略与方案对比 ​

学习目标

  • 掌握记忆"读、写、忘"三个环节各自的可选策略
  • 能对比摘要记忆、向量记忆、结构化画像、图记忆等方案的优缺点
  • 了解 mem0、Letta、LangGraph Store 等开源方案的定位
  • 能根据业务场景组合出合适的记忆架构

前三篇分别讲了 记忆的分类、短期记忆 和 长期记忆。这一篇不写新代码，而是站高一层：把各种做法放在一起比较，帮你在真实项目里做选择。本文是概念性文章，没有可运行代码。

读策略：记忆什么时候进入上下文 ​

策略做法优点缺点
总是注入每次请求都把画像 / 摘要拼进 system prompt简单、确定，不会漏占用固定 Token；内容多了就不可行
每轮检索用当前用户输入去检索 Top-K 记忆再注入只带相关内容，可扩展到海量记忆每轮多一次检索；检索不准就会带入噪声
按需调用提供 search_memory 工具，模型自己决定是否查不需要时零开销，灵活依赖模型判断，可能该查的时候不查

实践中常见的组合是：小而关键的画像总是注入，大量的情景记忆每轮检索或按需调用。

"每轮检索"还有个细节：直接拿用户这一句话去检索，效果经常不好。比如用户说"那第二种呢？"，这句话本身几乎没有语义信息。可以先用 LLM 结合最近几轮对话把它改写成完整的查询，再去检索。这和 RAG 中的查询改写是同一个思路。

写策略：什么时候写、写成什么样 ​

写入时机：

  • 热路径同步写：每轮对话后立即提取。实时，但增加延迟，且只看到局部信息。
  • 后台异步写：会话结束或闲置后批量提取。不影响响应，看到的上下文更完整，是多数产品的选择。
  • 显式触发：用户说"记住……"或模型调用 save_memory 工具时写入。

写入形态，按加工程度从低到高：

text
原始对话  ──►  摘要  ──►  事实条目  ──►  结构化画像 / 知识图谱
 (信息全)                                    (信息少，但最干净、最易用)
 (噪声多)                                    (加工成本最高)

加工得越多，读取时越好用，但信息损失越大，写入成本也越高。一个稳妥的做法是：原始对话归档保存（用于审计和重新提取），上下文里只用加工后的形态。这样当提取逻辑升级时，可以从原始数据重新生成记忆。

遗忘策略：记忆也需要清理 ​

很多人只考虑"怎么记住"，忘了"怎么忘掉"。记忆只增不减，迟早会出现过时信息、矛盾信息和大量低价值噪声。

  • 覆盖：同一属性出现新值时替换旧值。画像天然支持；记忆条目需要在写入时先检索相似条目，让 LLM 判断是新增、更新、删除还是忽略。
  • 衰减：检索打分里加入时近性，旧记忆的权重逐渐降低，但数据仍在。
  • 过期（TTL）：给某些类型的记忆设有效期，例如"用户这周在出差"。
  • 合并（Consolidation）：定期让 LLM 把大量零碎条目整理成少量高层结论，类似人在睡眠中整理记忆。Generative Agents 中的"反思（Reflection）"就是这种机制。
  • 用户删除：用户主动要求删除的记忆必须真正删除，包括向量索引里的副本。

方案对比 ​

方案写入读取优点缺点适合场景
滑动窗口无需加工最近 N 轮全量零成本、零失真早期信息全丢短对话、闲聊
摘要记忆LLM 滚动压缩摘要全量注入实现简单，保留主线细节丢失，多次压缩会漂移单会话内的长对话

开源方案速览 ​

下面只做定位层面的介绍，具体 API 和功能变化较快，以各项目官方文档为准。

  • mem0：一个面向 Agent 的记忆层，提供开源库和托管服务。核心思路是用 LLM 从对话中提取事实，与已有记忆比对后决定新增、更新或删除，底层可接多种向量库，也支持图存储。和上一篇手写的"变更集"思路一致，只是更完善。
  • Letta（原 MemGPT）：把上下文窗口当作"内存"、外部存储当作"磁盘"。Agent 通过工具调用自主编辑常驻上下文的记忆块，并把不常用的信息换出到外部存储。适合想让 Agent 自主管理记忆的场景。
  • Zep / Graphiti：基于时序知识图谱的记忆方案，强调事实随时间的变化（某个关系何时成立、何时失效）。Graphiti 是其开源的图谱构建库。
  • LangGraph：区分两层。Checkpointer 按线程（thread）持久化图的状态，相当于短期记忆；Store 提供跨线程的键值 / 语义检索存储，用于长期记忆。详见 LangGraph。
  • 其他框架：LlamaIndex、OpenAI Agents SDK、Spring AI、LangChain4j 等也都提供会话记忆相关的抽象，多数聚焦于对话历史管理，长期记忆通常需要自己接存储。见 框架全景与选型。

选择第三方方案前，问自己三个问题：数据存在哪里、能否私有化部署？提取逻辑能否定制和评估？出问题时能否看到"为什么记住了这条 / 为什么没检索到"？

按场景组合 ​

没有一种方案能包打天下，真实系统基本都是组合。下面是几个典型场景的参考架构：

text
场景 A：客服机器人（单次会话为主）
  短期：滑动窗口（最近 10 轮）+ 关键字段（订单号、手机号）结构化保存
  长期：几乎不需要；历史工单从业务系统查询，而不是靠"记忆"

场景 B：个人助理 / 陪伴类应用（跨会话、强个性化）
  短期：最近 N 轮原文 + 滚动摘要
  长期：结构化画像（每次注入）+ 情景记忆向量库（每轮检索，带时近性）
  后台：会话结束后提取；定期合并精简

场景 C：Coding Agent（长任务、项目级）
  短期：上下文压缩 + 工具结果截断 + 计划清单外置到文件
  长期：项目规则文件（程序记忆，人可编辑）+ 少量用户偏好

一个容易被忽视的原则：能从业务系统查到的，不要放进记忆。订单状态、账户余额这类信息有权威数据源，应该通过 Tool Calling 实时查询。记忆里的副本会过时，而且不可信。

选型时可以按下面的顺序思考：

  1. 是否真的需要跨会话记忆？很多场景短期记忆就够了。
  2. 需要记住的信息是"每次都用"还是"偶尔用"？前者用画像，后者用检索。
  3. 信息之间是否有复杂关系、是否随时间变化？是的话考虑图记忆。
  4. 团队是否有精力自研和评估？没有的话可以先用成熟的记忆层服务，但要确认数据合规。

常见坑 ​

  • 过早上复杂方案：还没验证用户需要记忆，就上图数据库和多级记忆。先用画像 + 摘要跑通，再根据 bad case 加能力。
  • 记忆与业务数据重复：把可以实时查询的数据存成记忆，导致记忆和数据库不一致。
  • 只看单次效果：记忆系统的问题往往在几十次会话后才暴露，例如画像膨胀、矛盾累积。评估时要模拟长期使用。
  • 检索结果全部注入：Top-K 里可能有低分噪声，设置相似度阈值，宁缺毋滥。
  • 黑盒方案不可排查：用第三方记忆层时，要能导出、查看、删除记忆，否则用户投诉"它为什么这么说"时无从下手。

小测 ​

1. 为什么建议保留原始对话归档，即使上下文里只用加工后的记忆？

查看答案

加工（摘要、提取）会丢信息，而且提取逻辑会不断迭代。保留原始数据，可以在提取逻辑升级后重新生成记忆，也便于审计和排查问题。注意归档本身也要遵守隐私和删除要求。

2. 某电商客服 Agent 想"记住用户的订单状态"，应该怎么做？

查看答案

不应该把订单状态写进记忆。订单状态的权威来源是订单系统，且会实时变化，应该提供查询工具，在需要时实时查询。记忆里最多保存"用户最近咨询过的订单号"这类线索。

3. 向量记忆和结构化画像分别更擅长什么？

查看答案

向量记忆擅长在大量非结构化内容中按语义找相关信息，适合情景记忆；结构化画像擅长存储精确、需要覆盖更新的事实和偏好，读取确定、无需检索，适合每次都要用的信息。
