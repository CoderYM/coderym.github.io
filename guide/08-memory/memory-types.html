记忆的分类 ​

学习目标

  • 理解大模型本身"没有记忆"，Agent 的记忆全部是工程手段拼出来的
  • 掌握短期记忆、长期记忆，以及语义、情景、程序三类长期记忆的区别
  • 能把一个具体业务需求映射到合适的记忆类型和存储方式
  • 了解记忆系统设计时要回答的几个关键问题

模型本身是无状态的 ​

先澄清一个最常见的误解：大模型 API 是无状态的。每一次 chat.completions.create 调用，模型只能看到你这次请求里传进去的 messages。你觉得 ChatGPT "记得"上一句话，是因为客户端把整段历史又发了一遍。

所以，Agent 的"记忆"本质上只有一件事：在合适的时机，把合适的信息放进上下文窗口。区别只在于信息从哪来、存在哪、怎么挑。

模型的参数里当然也存着大量"知识"（参数记忆，Parametric Memory），但它只能通过训练或微调改变，对应用开发者来说基本是只读的。本模块讨论的都是参数之外、由应用控制的外部记忆。

按时间跨度：短期 vs 长期 ​

维度短期记忆（Short-term）长期记忆（Long-term）
生命周期一次会话 / 一个任务内跨会话、跨天甚至永久
典型内容对话历史、工具调用结果、当前计划用户偏好、事实、历史经验、知识
存放位置进程内存、Redis、会话表关系库、KV、向量库、图数据库
进入上下文的方式基本全量（超长时截断或摘要）按需检索，只取相关的一小部分
主要难点窗口有限，怎么裁剪写什么、怎么检索、如何更新和遗忘

短期记忆可以类比人的工作记忆：容量小、正在处理的东西都在这里。对 Agent 来说，它就是当前的 messages 列表，加上 Agent 循环中的中间状态（例如计划清单、已完成的步骤）。

长期记忆则需要一个独立的存储，以及一套"写入 → 检索 → 注入上下文"的流程。没有检索这一步，长期记忆就退化成"把所有东西塞进 prompt"，很快就会撞上窗口上限和成本问题。

长期记忆的三种类型 ​

认知科学把长期记忆分为语义记忆、情景记忆和程序记忆，这个划分在 Agent 领域被广泛借用（例如 LangGraph 文档和 CoALA 论文都采用了类似的划分）。它的价值在于：不同类型的记忆，适合的存储和检索方式不一样。

语义记忆（Semantic Memory）：事实 ​

"用户叫张三，是后端工程师，主要用 Go"；"公司报销上限是每月 2000 元"。这类记忆是与时间无关的事实，通常有明确的主体和属性。

  • 适合存储：结构化字段（用户画像表、JSON 文档），或"事实条目"列表
  • 适合检索：按用户 ID 直接读取；条目多时用向量检索
  • 关键问题：冲突和更新。用户上个月说"在用 Java"，这个月说"转 Go 了"，要覆盖而不是并存

情景记忆（Episodic Memory）：经历 ​

"上周二用户让我排查一个 K8s 的 OOM 问题，最后发现是 JVM 堆参数配置错误"。这类记忆是带时间和上下文的事件，像日记。

  • 适合存储：带时间戳的事件记录、对话摘要，配合向量索引
  • 适合检索：语义相似度 + 时间衰减（越近越重要）
  • 典型用途：Few-shot 示例（"上次类似任务是这么做成功的"）、延续之前的话题

斯坦福的 Generative Agents 论文就是情景记忆的经典案例：每个角色有一条"记忆流"，检索时综合考虑相关性、时近性、重要性三个分数。

程序记忆（Procedural Memory）：怎么做 ​

"这个用户喜欢先看结论再看细节"；"部署这个服务时必须先跑数据库迁移"。这类记忆是行为规则和技能。

  • 适合存储：直接写进 system prompt 或规则文件，例如 Claude Code 的 CLAUDE.md、各类 Coding Agent 的项目规则文件
  • 更新方式：Agent 自我反思后改写指令，或者由人维护
  • 广义上，模型权重和工具代码也属于程序记忆

一张映射表 ​

把一个"个人编程助手"的需求拆开，看看每条信息该放在哪：

需求记忆类型推荐实现
记住这轮对话前面说过的话短期messages 列表，超长后摘要
记住用户的技术栈和职级语义（长期）用户画像表，每次请求注入
记住用户"回答要简短"的偏好程序（长期）写入 system prompt 的偏好段
"上次那个报错后来怎么解决的？"情景（长期）会话摘要 + 向量检索
公司内部文档、API 手册知识（外部）RAG 知识库，见 RAG 全景

注意最后一行：RAG 知识库和长期记忆在技术上很像（都会用到向量检索），但定位不同。知识库是"世界知道的东西"，通常由管理员导入、所有用户共享；记忆是"Agent 和某个用户之间发生过的事"，按用户隔离、由对话自动产生。混在一个索引里，常常会出现 A 用户的偏好被检索给 B 用户的事故。

设计记忆系统要回答的问题 ​

不管选什么方案，下面五个问题都绕不开：

  1. 写什么：全量对话都存，还是只存提炼后的事实？谁来提炼（规则、LLM）？
  2. 什么时候写：每轮对话后同步写（"热路径"），还是会话结束后异步写（"后台"）？
  3. 怎么读：每次都读，还是由 Agent 通过工具主动查询？取多少条？
  4. 怎么更新和遗忘：新事实与旧事实冲突怎么办？过期的信息要不要删？
  5. 隔离与合规：记忆按什么维度隔离（用户、租户、项目）？用户能否查看和删除自己的记忆？

后面三篇会逐一展开：短期记忆与会话管理 讲第 1 层，长期记忆与用户画像 讲写入与检索，记忆读写策略与方案对比 讲各种方案的取舍。

常见坑 ​

  • 以为模型会记住：API 是无状态的，忘了传历史是新手最常见的 bug，表现为"模型每轮都像第一次见面"。
  • 一切都塞进向量库：用户姓名、职级这种确定的结构化事实，直接用数据库字段存取更准确，没必要靠语义相似度去"碰"。
  • 记忆和知识库混用：不做用户隔离，就有隐私泄露风险。
  • 只写不删：记忆越来越多，过时、矛盾的信息会持续污染上下文，效果反而越来越差。
  • 把记忆当成可信输入：记忆内容可能来自用户输入，甚至来自被注入的网页内容，它和用户消息一样不可信，不能让它绕过权限检查。

小测 ​

1. 用户说"以后回答都用英文"，这条信息属于哪类记忆？最合适放在哪里？

查看答案

属于程序记忆（行为偏好）。最合适的做法是写入用户偏好存储，每次请求时拼进 system prompt，而不是放在向量库里等待检索，因为它每次都需要生效。

2. 为什么说"把所有历史对话都塞进 prompt"不是一个长期记忆方案？

查看答案

上下文窗口有限，历史会持续增长；即使窗口够大，Token 成本和延迟也会线性上涨，而且无关内容过多会降低模型对关键信息的注意力。长期记忆的核心是"存储 + 按需检索"，只把相关的少量信息放进上下文。

3. 企业知识库和用户长期记忆都用向量检索，为什么建议分开存储？

查看答案

两者的来源、共享范围和生命周期不同：知识库由管理员维护、全员共享；记忆由对话产生、按用户隔离、需要支持更新和删除。分开存储便于做权限隔离和独立的更新策略，避免跨用户泄露。
