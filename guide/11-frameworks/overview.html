框架全景与选型 ​

学习目标

  • 理解 Agent 框架到底帮你做了什么，以及什么时候不需要框架
  • 认识 Python、Go、Java 三个生态中主流框架的定位
  • 掌握一套可落地的选型方法，而不是跟风选"最火"的那个
  • 了解使用框架时如何控制锁定风险

先问：需要框架吗 ​

如果你跟着本站做过 不用框架手写 Agent，会发现一个能用的 Agent 核心只有几十行：调模型、解析工具调用、执行工具、追加消息、循环。那框架的价值在哪？

框架真正帮你省事的，是这些"手写也能做，但做好很费劲"的部分：

能力手写难度框架通常提供
多模型适配低（OpenAI 兼容接口已覆盖大部分）统一的模型抽象，切换厂商改一行
工具定义中（手写 JSON Schema 容易出错）从函数签名、注解自动生成 Schema
状态持久化与恢复高Checkpoint，任务中断后从断点继续
人在环路高在指定步骤暂停，等待人工审批后恢复
复杂流程编排高图、分支、并行、子流程
可观测性中内置 Trace，对接 LangSmith、Langfuse 等
RAG 管道中文档加载、切分、索引、检索的现成组件

所以判断标准很简单：

一个务实的建议：先手写一遍，理解原理后再上框架。这样框架出问题时，你知道它底层在干什么，也能判断某个抽象是在帮你还是在碍事。

三个生态的主流框架 ​

Python：选择最多 ​

Python 是 Agent 生态的主战场，几乎所有新框架都先出 Python 版。

框架定位适合
LangGraph以"状态图"建模 Agent，强调可控性、持久化、人在环路复杂、长流程、需要精确控制的生产级 Agent
LangChain模型、工具、检索等组件的集成库，v1 起以 create_agent 为主入口，底层基于 LangGraph快速搭建、需要丰富集成
OpenAI Agents SDK轻量：Agent、工具、交接（handoff）、护栏快速搭建多 Agent 原型，概念少
Claude Agent SDK把 Claude Code 的 Agent 运行时作为库提供，自带文件、命令等工具编码、运维、文件处理类 Agent
LlamaIndex以数据和检索为中心RAG、文档问答、知识库
CrewAI角色扮演式多 Agent 团队内容生产、调研等流程清晰的多角色协作
AutoGen微软出品的多 Agent 对话框架研究和实验多 Agent 对话模式

Go：云原生与高并发 ​

Go 生态更注重性能、类型安全和工程化，框架数量少但质量不错。

框架定位适合
Eino字节跳动 CloudWeGo 开源，组件 + 编排（Chain / Graph），强类型国内大厂风格的生产级 Go 服务
langchaingo社区维护的 LangChain Go 移植熟悉 LangChain 概念、需要较多集成
官方 SDK + 手写openai-go 等官方 SDK 或直接 HTTP需求简单、追求可控和零依赖

Java：企业级集成 ​

Java 生态的优势在于和现有企业系统（Spring、数据库、消息队列、权限体系）的无缝集成。

框架定位适合
Spring AISpring 官方项目，ChatClient 流式 API、自动配置、Advisor 机制已经是 Spring Boot 技术栈的团队
LangChain4j独立于 Spring，AiServices 声明式接口非 Spring 项目，或偏好声明式写法
Spring AI Alibaba基于 Spring AI，加强了阿里云生态和多 Agent 编排使用通义千问、阿里云的团队

无代码与低代码 ​

Dify、Coze 等平台用可视化方式搭建 Agent 和工作流，适合业务人员快速验证想法，也能通过 API 嵌入到业务系统中。

最后一行往往是决定性的：团队主力语言和现有基础设施，比框架本身的功能差异更重要。一个 Java 团队为了用 LangGraph 引入 Python 服务，换来的是两套部署、两套监控和跨语言调用的复杂度。反过来，如果 Agent 是一个独立的新服务、团队也有 Python 能力，Python 生态的丰富度就是实实在在的优势。

选型的五个问题 ​

  1. 语言与基础设施：团队用什么语言？Agent 要和哪些现有系统打交道？
  2. 控制力需求：你需要精确控制每一步（选图编排类），还是让模型自己决定流程（选轻量 Agent 类）？
  3. 持久化与人在环路：任务会跑多久？要不要中途审批？这是手写最难做好的部分。
  4. 模型绑定：框架是否支持你要用的模型厂商（尤其是国内模型）？OpenAI 兼容接口通常是最大公约数。
  5. 成熟度与活跃度：版本是否稳定、文档是否跟得上、社区是否活跃、最近半年是否有破坏性变更。

控制锁定风险 ​

Agent 框架普遍迭代很快，一年内出现大版本的破坏性变更是常态。几个降低风险的做法：

  • 业务逻辑与框架解耦：工具函数写成普通函数，提示词放在独立文件，框架只负责"粘合"。换框架时这些都能复用。
  • 工具用 MCP 暴露：把工具做成 MCP Server，任何框架都能接入。
  • 锁定版本：依赖写精确版本，升级前跑一遍 回归测试。
  • 评估先行：有了 评估集，换框架、换模型时才知道效果有没有退化。

常见坑 ​

  • 为了用框架而用框架：三个工具的简单 Agent 引入一个重型框架，调试时要穿过好几层抽象才能看到真实的 prompt。
  • 看过时教程：框架 API 变化快，搜到的博客可能是一年前的写法。以官方文档和你锁定的版本为准。
  • 混用多个框架：一个项目里同时用 LangChain、LlamaIndex 和 CrewAI，各自有一套消息格式和工具抽象，组合起来很难维护。
  • 忽略框架发出的真实请求：框架会在背后拼接系统提示词、改写工具描述。开启 Trace 看清实际发给模型的内容，参考 轨迹追踪与可观测性。

小测 ​

  1. 一个 Agent 只需要调用 3 个内部 API 回答员工问题，团队用 Go，你会怎么选？
查看答案

优先考虑手写或用轻量方案：Go 标准库调用 OpenAI 兼容接口加一个简单循环即可；如果希望少写样板代码，可以用 Eino 的 ReAct Agent。不需要引入复杂的图编排。

  1. 什么样的需求最能体现 LangGraph 这类图编排框架相对手写的价值？
查看答案

长时间运行、需要中断后恢复（Checkpoint）、需要在特定步骤等待人工审批、流程有复杂分支或循环的场景。这些手写需要自己实现状态持久化和恢复逻辑，成本高且容易出错。

  1. 列举两种降低框架锁定风险的做法。
查看答案

例如：工具和业务逻辑写成与框架无关的普通函数或 MCP Server；提示词独立管理；锁定依赖版本；建立评估集，升级或迁移框架时用回归测试验证效果。
