为什么评估是第一优先级 ​

学习目标

  • 理解为什么 Agent 开发离不开系统化评估，而"手动试几下"不够用
  • 区分离线评估、在线评估和人工评审各自解决什么问题
  • 知道评估要测什么：最终结果、过程轨迹、成本与延迟
  • 能在项目第一周就搭起一个最小评估闭环

一个常见的场景 ​

你写了一个客服 Agent，测试了十几个问题，效果不错，上线了。两周后，产品同学说"退款问题经常答错"。你改了系统提示词，加了一句"涉及退款时必须先查询订单状态"，手动试了三个退款问题，都对了，发布。

第二天，有用户反馈：查物流的问题现在也会先去查订单状态，多花了一轮工具调用，响应慢了好几秒；还有一部分售后问题开始答非所问。

问题出在哪里？不在提示词本身，而在于你没有办法知道一次改动对整体行为的影响。三个手动测试只覆盖了你刚想到的情况，而 Agent 的行为空间远比这大。

Agent 为什么特别需要评估 ​

传统软件的函数给定输入就有确定输出，单元测试能覆盖主要分支。Agent 不一样：

特点传统软件LLM Agent
输出确定性相同输入相同输出同一输入多次运行结果可能不同
正确性判断assert a == b 即可答案常是自然语言，"对"有多种写法
影响范围改一个函数影响可追踪改一句提示词可能影响所有任务
执行路径代码分支固定模型自己决定调用哪些工具、调几次
依赖变化依赖版本可锁定模型服务端升级，行为可能悄悄变化

这几点叠加起来，结论很直接：凭感觉开发 Agent，等于闭着眼睛调参。你没法回答"这次改动让成功率从多少变到了多少"，也就没法做出可靠的工程决策。

Anthropic 在 Building effective agents 中也反复强调：先从简单方案开始，用评估衡量效果，只有在评估证明复杂度带来收益时才增加复杂度。没有评估，这条原则根本无法执行。

评估要测什么 ​

Agent 的评估可以分三层来看：

text
┌─────────────────────────────────────────────┐
│ 1. 结果层：最终答案对不对？任务完成了没有？    │
├─────────────────────────────────────────────┤
│ 2. 过程层：调用了哪些工具？参数对不对？         │
│            有没有多余步骤、死循环、越权操作？    │
├─────────────────────────────────────────────┤
│ 3. 代价层：花了多少 Token、多少秒、多少次调用？  │
└─────────────────────────────────────────────┘

  • 结果层最重要，也是用户唯一直接感知的。比如"用户问订单 A123 的物流，回答里有正确的快递单号"。
  • 过程层用来定位问题和防止隐患。答案对了但调用了一个不该调用的删除工具，这依然是严重缺陷。
  • 代价层决定能不能上线。成功率 95% 但每次要 40 秒、花 2 万 Token 的方案，很多场景下不可用。

只看结果层，你会错过"碰巧答对"和"代价失控"；只看过程层，你会陷入优化中间步骤却不改善最终效果。三层都要有，但第一周可以只做结果层。

三种评估方式 ​

方式何时进行优点局限
离线评估开发时、合并前，跑固定数据集可重复、可对比、可放进 CI数据集覆盖不到所有真实情况
在线评估上线后，基于真实流量反映真实分布需要埋点，有延迟，难以做对照
人工评审定期抽样最接近真实质量判断慢、贵、难规模化

为什么是"第一"优先级 ​

很多团队把评估放在"功能做完之后"。这样做的代价是：

  1. 无法比较方案。要不要换更大的模型？要不要加 RAG？要不要拆成多 Agent？没有评估，这些讨论只能靠争论和直觉。
  2. 不敢改动。系统越复杂，越没人敢动提示词，因为不知道会坏掉什么。
  3. 模型升级变成赌博。厂商发布新版本时，你无法在一小时内回答"能不能切换"。
  4. 问题反馈无法沉淀。用户报告的 bug 修完就忘，下次改动又会复发。

反过来，有了评估之后，提示词、模型、工具设计都变成了可以实验的变量：改一处，跑一遍，看数字。这和机器学习里"先定好验证集再训练"是同一个道理。

第一周的最小评估闭环 ​

不需要一开始就上平台、上 LLM-as-Judge。下面这个起步方式足够大多数项目用上一段时间：

  1. 收集 20~50 个真实用例。来源可以是产品需求文档里的示例、内测用户的提问、你自己能想到的边界情况。每条写下输入和"什么样算对"。
  2. 用最简单的判定方式。能精确匹配就精确匹配；不能就检查"回答里是否包含关键事实"、"是否调用了某个工具"。
  3. 写一个脚本批量跑。输出通过率和失败用例列表，失败用例要能直接看到模型的完整回答。
  4. 每次改动前后都跑。把结果数字记在提交信息或表格里。
  5. 每修一个 bug 就加一条用例。

用例格式可以就是一个 JSONL 文件：

常见坑 ​

  • 只测"开心路径"。用例全是格式规范、意图清晰的问题，真实用户的错别字、多意图、无关闲聊一个都没有。至少留 20% 用例给边界和对抗情况。
  • 用例和提示词一起改。为了让通过率好看而修改期望答案，评估就失去了意义。期望答案变更应当单独评审。
  • 只跑一次就下结论。模型输出有随机性，一个用例 5 次里对 3 次，单次运行可能显示"对"也可能显示"错"。关键用例应多次运行看稳定性，或者用 temperature=0 降低（但不能消除）波动。
  • 把评估当成一次性任务。数据集不随线上问题更新，几个月后就和真实分布脱节。
  • 只看总分。总通过率从 82% 到 83%，可能是 10 个用例变好、9 个变坏。要看逐条差异。

小测 ​

  1. 你把提示词改了一句，手动测了 3 个相关问题都正确。为什么这不足以说明改动是好的？
查看答案

因为改动可能影响其他类型的任务（提示词作用于全部请求），而 3 个用例只覆盖了你关心的那一类；同时模型输出有随机性，3 次正确不代表稳定正确。需要在覆盖多种任务的固定数据集上对比改动前后的结果，并检查逐条差异。

  1. 一个 Agent 的最终回答完全正确，但过程中调用了一次 delete_file 工具后又恢复了文件。只看结果层评估会漏掉什么？
查看答案

会漏掉过程层的风险：Agent 执行了不必要的危险操作。在生产环境中这类操作可能不可逆，或者恢复失败。过程层评估（检查工具调用序列、禁止调用的工具）能发现这个问题。

  1. 离线评估、在线评估、人工评审之间是什么关系？
查看答案

它们互相补充、形成循环：离线评估在每次改动时快速、可重复地守住质量；在线评估反映真实流量下的表现；人工评审提供最可信的质量判断。线上和人工发现的失败案例应补充进离线数据集。
