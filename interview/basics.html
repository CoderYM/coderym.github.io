基础概念题 ​

本页共 22 题，覆盖 Agent 开发最常被问到的基础概念。建议先独立作答，再展开参考答案对照。

大模型基础 ​

1. 什么是 Token？为什么 Agent 开发者需要关心 Token？ ​

参考答案

Token 是模型处理文本的基本单位，由分词器把文本切分得到，可能是一个词、一个子词或一个字符。中文通常一个汉字对应一个或多个 Token，具体取决于分词器。

开发者需要关心 Token，因为：

  • 上下文窗口按 Token 计算，超过上限会报错或被截断。
  • 计费按 Token 计算，输入和输出往往分开计价。
  • 延迟与输出 Token 数近似成正比。
  • Agent 的多轮循环会不断累积工具结果和历史消息，Token 量增长很快，是成本和稳定性问题的主要来源。

参考：Token 与上下文窗口

2. temperature 和 top_p 分别控制什么？Agent 场景一般怎么设置？ ​

参考答案

两者都控制采样的随机性：

  • temperature 调整概率分布的"尖锐程度"。越低越倾向选择概率最高的 Token，输出更确定；越高分布越平，输出更多样。
  • top_p（核采样）只在累计概率达到 p 的最小候选集合中采样，截掉长尾的低概率 Token。

Agent 场景中，工具选择、参数生成、结构化输出等需要稳定性的环节通常用较低的 temperature；创意写作、头脑风暴可以调高。一般只调其中一个，不要同时大幅调整两者。另外，即使 temperature 为 0，也不能保证输出完全确定。部分推理模型会限制或忽略这些参数，以厂商文档为准。

参考：采样参数：temperature、top_p

3. 大模型为什么会产生幻觉？在应用层有哪些缓解手段？ ​

参考答案

模型的训练目标是生成"看起来合理"的下一个 Token，而不是"保证正确"。当模型缺少相关知识、知识过时、或者问题本身有歧义时，它仍会生成流畅的回答，这就是幻觉。

应用层的缓解手段：

  • 用 RAG 或工具调用提供可靠的外部信息，并要求模型基于资料作答、附上引用。
  • 在提示词中允许模型说"不知道"，并明确资料不足时的处理方式。
  • 对关键事实用确定性工具（数据库查询、计算器）获取，不让模型凭记忆回答。
  • 输出后做校验：结构校验、规则校验，或用另一个模型做事实核查。
  • 建立评估集，持续监测幻觉率。

4. 推理模型（Reasoning Model）和普通对话模型在使用上有什么不同？ ​

参考答案

推理模型在给出最终答案前会进行一段较长的内部推理（扩展思考），擅长数学、代码、复杂规划等多步推理任务。

使用上的主要差别：

  • 提示词更简洁： 不需要再写"一步一步思考"或详细的推理步骤示例，给清楚目标和约束即可。
  • 延迟和成本更高： 推理过程会消耗额外的 Token，响应时间更长。
  • 参数限制： 部分推理模型不支持或限制 temperature 等采样参数，有的提供"推理强度"或"思考预算"参数。
  • 适用场景不同： 简单的分类、提取、闲聊用普通模型更划算；复杂规划、疑难问题用推理模型。

实践中常见的做法是混合使用：用推理模型做规划或难点决策，用较快的模型执行简单步骤。

参考：推理模型与扩展思考

5. 什么是 Embedding？它和大模型生成文本有什么关系？ ​

参考答案

Embedding 是把文本（或图片等）映射成一个固定长度的稠密向量，语义相近的内容在向量空间中距离更近。通常由专门的 Embedding 模型生成，而不是对话模型。

它和文本生成是两类不同的能力：生成模型负责"写"，Embedding 模型负责"表示"。在 Agent 中，Embedding 主要用于语义检索（RAG）、记忆检索、去重、聚类和分类。需要注意，同一个索引里的向量必须由同一个 Embedding 模型生成，换模型需要重建索引。

参考：Embedding 与向量语义

提示词 ​

6. 系统提示词（System Prompt）和用户消息有什么区别？一个好的系统提示词包含哪些部分？ ​

参考答案

系统提示词用于设定模型的角色、行为规则和全局约束，在整个对话中持续生效，模型通常会给予它更高的优先级。用户消息是具体的输入和请求。

一个好的系统提示词一般包含：

  • 角色与目标：你是谁，为谁服务，要达成什么。
  • 背景信息：业务上下文、可用资源、当前日期等。
  • 行为规则：必须做什么、禁止做什么、遇到不确定时怎么办。
  • 工具使用说明：什么情况下用哪个工具。
  • 输出格式要求。

注意不要把机密信息放在系统提示词里，它可能被 Prompt 注入套取。

参考：系统提示词与角色设计

7. 如何让模型稳定输出 JSON？ ​

参考答案

按可靠性从高到低：

  1. 使用厂商提供的结构化输出能力，传入 JSON Schema，由模型服务端约束解码，基本能保证格式合法。
  2. 利用 Tool Calling，把期望的输出定义成一个工具的参数 Schema，让模型"调用"它。
  3. 提示词约束：明确给出 Schema 和示例，要求只输出 JSON。

无论用哪种方式，程序端都要做校验（如 pydantic），校验失败时把错误信息反馈给模型重试，并设置重试上限。格式合法不等于内容正确，字段值仍需要业务校验。

参考：结构化输出与 JSON Schema

8. Few-shot 和 Chain-of-Thought 分别解决什么问题？ ​

参考答案
  • Few-shot： 在提示词中给几个输入输出示例，让模型理解任务格式、风格和边界。适合"很难用语言描述清楚、但容易举例"的任务。示例要多样、有代表性，否则模型会过度模仿示例的表面特征。
  • Chain-of-Thought： 让模型先写出推理过程再给答案，提升多步推理任务的准确率，同时让推理过程可检查。

两者可以结合：给出带推理过程的示例。对推理模型，通常不需要再显式要求思维链。

参考：Few-shot 与思维链、Chain-of-Thought 论文精读

Agent 概念 ​

9. 什么是 Agent？它和 Chatbot、Workflow 有什么区别？ ​

参考答案

Agent 是由大模型驱动、能够根据目标自主决定下一步做什么、调用工具与环境交互，并循环执行直到完成任务的系统。

  • Chatbot： 一问一答，主要生成文本，不主动执行动作。
  • Workflow： 由开发者预先定义好执行路径，模型只在某些节点上完成具体子任务，流程是确定的。
  • Agent： 执行路径由模型在运行时动态决定，步数和顺序不固定。

选择原则：流程固定、可枚举的任务优先用 Workflow，更可控、更便宜；路径无法预先确定、需要根据中间结果灵活调整的任务才用 Agent。

参考：Agent 到底是什么、Agent、Chatbot 与 Workflow 的区别

10. 一个 Agent 由哪些核心组件构成？ ​

参考答案

常见的拆分方式：

  • 模型： 负责理解、推理和决策。
  • 工具： Agent 与外部世界交互的手段，如搜索、数据库、API、代码执行。
  • 循环控制： 调用模型、执行工具、更新状态、判断是否结束的主循环，以及步数和预算限制。
  • 上下文与记忆： 决定每一轮给模型看什么信息，包括系统提示词、对话历史、工具结果、检索到的知识和长期记忆。
  • 护栏与权限： 输入输出检查、工具权限控制、人工确认。

此外，生产环境还需要评估和可观测性作为配套。

11. Tool Calling 的完整流程是什么？模型真的"执行"了工具吗？ ​

参考答案

模型并不执行工具，它只负责生成"要调用哪个工具、传什么参数"的结构化请求，执行由你的代码完成。完整流程：

  1. 开发者在请求中传入工具定义（名称、描述、参数 JSON Schema）和用户消息。
  2. 模型判断需要调用工具，返回一个或多个工具调用请求，包含工具名、参数和调用 ID。
  3. 应用代码解析请求，校验参数，执行对应的函数。
  4. 把执行结果（或错误信息）作为工具结果消息，带上调用 ID，追加到消息列表中。
  5. 再次调用模型，模型根据结果决定继续调用工具还是给出最终回答。

参考：工具调用原理

12. 如何设计一个好用的工具？ ​

参考答案
  • 名称和描述清晰： 描述要说明工具做什么、什么时候该用、什么时候不该用，这是模型选择工具的唯一依据。
  • 参数简单明确： 用枚举限制取值，给出格式说明和示例，避免模型猜测。
  • 粒度合适： 一个工具完成一件完整的事，避免过于细碎导致调用次数爆炸，也避免一个工具包揽太多。
  • 返回精简： 只返回模型做决策需要的信息，大结果做分页或截断。
  • 错误可读： 失败时返回清晰的错误原因和修正建议，而不是抛出堆栈。
  • 安全： 区分只读和写操作，写操作做权限控制和确认，尽量保证幂等。

参考：工具设计原则、SWE-agent 论文精读

13. 解释 ReAct 模式。它有哪些常见的失败方式？ ​

参考答案

ReAct 让模型交替进行推理（Thought）和行动（Action），每次行动后获得观察结果（Observation），再基于结果继续推理，直到得出答案。推理帮助分解任务和调整计划，行动带回真实信息减少幻觉。

常见失败方式：

  • 反复调用同一个工具，陷入循环。
  • 工具返回无用或错误信息后，无法调整策略。
  • 贪心地一步步决策，长任务中偏离原始目标。
  • 过早结束，在信息不足时给出答案。

对应措施：最大步数和重复检测、更好的工具返回和错误提示、引入规划步骤、在结束前加自我检查。

参考：ReAct：推理与行动、ReAct 论文精读

14. ReAct 和 Plan-and-Execute 有什么区别？各自适用什么场景？ ​

参考答案
  • ReAct： 每一步都由模型根据最新观察决定下一步，灵活，适合步骤少、需要根据中间结果频繁调整的任务。缺点是缺少全局规划，每一步都要调用一次大模型。
  • Plan-and-Execute： 先由规划器生成完整的步骤计划，再由执行器逐步执行，必要时重新规划。适合步骤较多、结构清晰的任务，可以让执行步骤使用更便宜的模型，计划本身也便于展示给用户确认。缺点是初始计划错了需要重规划机制，对动态变化的环境响应较慢。

实践中两者经常结合：先规划，每个步骤内部用 ReAct 执行。

参考：Plan-and-Execute

15. 如何防止 Agent 无限循环或成本失控？ ​

参考答案
  • 最大步数： 超过上限强制结束，并返回当前进展。
  • Token 和金额预算： 累计统计每次调用的消耗，超出预算即停止。
  • 超时： 整体任务和单个工具调用都要有超时。
  • 重复检测： 检测连续相同的工具调用和参数，提示模型换思路或直接终止。
  • 明确的完成条件： 在提示词中说明什么情况下应该结束，并提供一个"完成"动作或结构化最终输出。
  • 监控和告警： 线上统计步数分布和单次成本，发现异常。

参考：终止条件、步数与预算控制

上下文与记忆 ​

16. 什么是上下文工程？它和提示词工程有什么区别？ ​

参考答案

提示词工程关注"怎么写指令"，主要是静态的提示词文本。上下文工程关注"每一次调用模型时，上下文窗口里应该放什么"，是动态的：包括系统提示词、工具定义、检索到的知识、记忆、对话历史、工具结果，以及它们的顺序、长度和取舍。

Agent 的运行过程中上下文会不断增长，上下文工程要解决的问题是在有限的窗口和预算内，让模型始终看到完成当前步骤最需要的信息。

参考：什么是上下文工程

17. 对话历史太长时有哪些处理方法？ ​

参考答案
  • 滑动窗口： 只保留最近 N 轮，简单但会丢失早期信息。
  • 摘要压缩： 把早期对话总结成一段摘要，保留关键事实和决定。
  • 工具结果裁剪： 旧的工具返回往往占用最多，可以只保留摘要或删除。
  • 按需检索： 把历史存入外部存储，需要时再检索相关部分。
  • 重要信息外置： 用户偏好、任务状态等结构化信息单独维护，每次注入，不依赖历史消息。

需要注意，频繁改动上下文的前缀会降低 Prompt Caching 的命中率。

参考：上下文窗口管理、压缩与摘要

18. 什么是 Prompt Caching？怎样提高缓存命中率？ ​

参考答案

Prompt Caching 是模型服务端对请求中相同的前缀部分做缓存，后续请求命中缓存时可以降低延迟和成本。Agent 循环中，系统提示词、工具定义和早期历史每一轮都重复发送，非常适合缓存。

提高命中率的做法：

  • 把稳定不变的内容（系统提示词、工具定义、固定文档）放在最前面，变化的内容放在后面。
  • 不要在前缀中放时间戳、随机 ID 等每次都变的内容。
  • 对话历史只追加不修改。
  • 按厂商要求设置缓存断点（有的需要显式标记，有的自动处理）。

参考：Prompt Caching

19. Agent 的记忆可以分为哪几类？ ​

参考答案

一种常用的分法：

  • 短期记忆（工作记忆）： 当前会话中的消息和任务状态，存在于上下文窗口中。
  • 长期记忆： 跨会话保存的信息，存在外部存储中，需要时检索。可进一步细分为：
    • 语义记忆：事实和知识，如用户偏好、用户画像。
    • 情景记忆：过去发生的具体经历，如某次任务的过程和结果。
    • 程序记忆：做事的方法和规则，如学到的经验、更新后的提示词。

设计长期记忆时需要考虑：何时写入、写入什么、如何检索、如何更新和删除冲突或过时的记忆，以及用户隐私。

参考：记忆的分类、长期记忆与用户画像

协议与生态 ​

20. MCP 是什么？它解决了什么问题？ ​

参考答案

MCP（Model Context Protocol）是一个开放协议，规定了 AI 应用如何以统一的方式连接外部工具和数据源。

没有 MCP 时，每个 AI 应用都要为每个工具写一套集成代码，形成 M 个应用乘以 N 个工具的集成工作量。MCP 让工具提供方实现一次 MCP Server，任何支持 MCP 的应用都可以接入，变成 M 加 N。

核心角色：Host（AI 应用本身）、Client（Host 内与某个 Server 保持连接的组件）、Server（暴露能力的服务）。Server 可以暴露 Tools（可调用的函数）、Resources（可读取的数据）和 Prompts（提示词模板）。传输方式包括本地的 stdio 和远程的 HTTP。

参考：MCP 架构与核心概念

21. MCP 和 A2A 有什么区别？ ​

参考答案
  • MCP 解决的是"Agent 与工具 / 数据"之间的连接，Server 端通常是被动的能力提供者。
  • A2A（Agent2Agent）解决的是"Agent 与 Agent"之间的协作：一个 Agent 如何发现另一个 Agent 的能力、委托任务、跟踪任务状态并接收结果，对方是有自主能力的 Agent，可能是不同团队、不同框架实现的。

两者是互补关系：一个 Agent 可以通过 MCP 使用工具，同时通过 A2A 与其他 Agent 协作。

参考：A2A：Agent 之间的协议

22. 什么时候应该使用 Agent 框架，什么时候应该自己手写？ ​

参考答案

框架的好处：快速起步，内置状态管理、持久化、流式输出、可视化调试、人在环路等能力，生态集成丰富。

框架的代价：抽象层多，出问题时难以排查；版本变化快；对上下文和提示词的控制力下降；团队需要学习成本。

建议：

  • 先手写一遍核心循环，理解原理。
  • 简单的单 Agent、工具不多的场景，手写或使用轻量 SDK 就够了。
  • 需要复杂状态流转、长时间运行、断点恢复、人工审批的场景，使用 LangGraph 这类编排框架收益更大。
  • 无论用不用框架，都要确保能看到每次实际发送给模型的完整上下文。

参考：框架全景与选型、不用框架手写 Agent
