RAG 题 ​

本页共 20 题，覆盖 RAG 系统从离线建索引到在线检索、生成、评估的完整链路。

基本概念 ​

1. 什么是 RAG？为什么需要 RAG？ ​

参考答案

RAG（Retrieval-Augmented Generation，检索增强生成）是在生成回答之前，先从外部知识库中检索相关内容，再把检索结果和问题一起交给模型生成答案。

需要 RAG 的原因：

  • 模型的训练知识有截止时间，无法知道最新信息。
  • 模型不知道企业内部和用户私有的数据。
  • 直接依赖模型记忆容易产生幻觉，RAG 能让答案基于资料，并附上来源便于核实。
  • 相比微调，更新知识只需更新索引，成本低、实时性好，还能做权限控制。

参考：RAG 全景、RAG 原始论文精读

2. 描述一个 RAG 系统的完整流程。 ​

参考答案

分为离线和在线两条链路：

text
离线：文档 ──▶ 解析 ──▶ 清洗 ──▶ 切分 ──▶ Embedding ──▶ 写入向量库（含元数据）

在线：问题 ──▶ 查询改写 ──▶ 检索（向量 / 关键词） ──▶ 重排 ──▶ 组装上下文 ──▶ 生成答案 + 引用

每个环节都会影响最终效果：解析质量决定信息是否完整，切分决定检索粒度，Embedding 决定语义匹配能力，重排决定排序精度，提示词决定模型如何使用资料。

3. RAG 和微调分别适合什么场景？ ​

参考答案
  • RAG 适合： 知识频繁更新、需要引用来源、数据有权限隔离、知识量大的场景，比如企业知识库、客服、文档问答。
  • 微调适合： 改变模型的行为、风格、输出格式，或让模型掌握某个领域的特定任务模式，比如固定格式的抽取、特定语气的回复。

一个常用的判断：RAG 解决"模型不知道"的问题，微调解决"模型不会做"的问题。两者可以结合使用，但大多数应用应该先用 RAG 加提示词，确实不够时再考虑微调。

文档处理与切分 ​

4. 常见的切分策略有哪些？如何选择 chunk 大小？ ​

参考答案

常见策略：

  • 固定长度切分： 按 Token 或字符数切，配合重叠窗口。简单通用，但可能切断语义。
  • 递归 / 结构化切分： 优先按标题、段落、句子等自然边界切，超长再继续细分。
  • 按文档结构切分： Markdown 标题、HTML 标签、代码函数、表格行等。
  • 语义切分： 根据相邻句子的 Embedding 相似度变化寻找切分点。

chunk 大小的权衡：太小，单块缺乏上下文，检索到了也答不全；太大，语义被稀释，检索精度下降，还浪费上下文。没有通用的最优值，应该根据文档类型和问题类型，用评估集对比几种大小和重叠设置。

参考：文档解析与切分

5. PDF、表格、图片等复杂文档如何处理？ ​

参考答案
  • PDF： 区分文本型和扫描型。文本型用解析库提取，注意多栏布局、页眉页脚、跨页段落；扫描型需要 OCR。也可以使用版面分析工具识别标题、段落和表格。
  • 表格： 保留表结构，转成 Markdown 或 HTML 表格；大表可以按行切分，每块带上表头；也可以为表格生成一段文字描述用于检索。
  • 图片和图表： 用多模态模型生成描述文本再建索引，或使用多模态 Embedding。
  • 通用做法：在每个 chunk 的元数据中保留来源文件、页码、章节标题，便于引用和过滤。

参考：文档解析与切分、多模态输入：图片与文档

6. 切分后的 chunk 丢失了上下文怎么办？ ​

参考答案
  • 添加上下文前缀： 在每个 chunk 前加上文档标题、章节路径，或用模型为每个 chunk 生成一句说明它在全文中位置和主题的上下文。
  • 父子块（小块检索、大块返回）： 用小块做检索保证精度，命中后返回它所在的更大段落或父文档。
  • 重叠窗口： 相邻 chunk 之间保留一定的重叠。
  • 相邻扩展： 命中某个 chunk 后，把前后相邻的 chunk 一起放进上下文。

检索 ​

7. 向量检索的原理是什么？常用的相似度度量有哪些？ ​

参考答案

用 Embedding 模型把文档块和查询都编码成向量，在向量空间中找出与查询向量最接近的若干个文档向量。

常用的度量：余弦相似度、点积（内积）、欧氏距离。向量经过归一化后，余弦相似度和点积是等价的。选择哪一种通常取决于 Embedding 模型的训练方式，按模型文档的推荐来设置。

参考：Embedding 与向量语义

8. 什么是 ANN？常见的索引算法有哪些？ ​

参考答案

ANN（Approximate Nearest Neighbor，近似最近邻）用少量精度损失换取大幅的速度提升，因为在海量向量中做精确的暴力搜索太慢。

常见算法：

  • HNSW： 基于分层可导航小世界图，查询快、召回高，内存占用较大，是很多向量数据库的默认选择。
  • IVF： 先聚类，查询时只搜索最近的几个簇，可以配合量化。
  • PQ 等量化方法： 压缩向量以减少内存，代价是精度下降。

调参时要在召回率、延迟和内存之间权衡，比如 HNSW 的构建和搜索参数、IVF 搜索的簇数量。

参考：向量数据库

9. 如何选择向量数据库？ ​

参考答案

考虑因素：

  • 数据规模和性能： 向量数量、QPS、延迟要求。
  • 功能： 元数据过滤、混合检索、多租户、增量更新和删除。
  • 运维： 托管服务还是自建，团队是否已经有相关基础设施。
  • 成本和与现有技术栈的集成。

常见选择：数据量不大且已经使用 PostgreSQL 时，pgvector 往往是最省心的方案；需要大规模、高性能、丰富功能时，选择 Milvus、Qdrant、Weaviate 等专用向量数据库或托管服务；原型阶段可以用 Chroma 或 FAISS 等轻量方案。

参考：向量数据库

10. 为什么需要混合检索？如何融合两路结果？ ​

参考答案

向量检索擅长语义匹配，但对专有名词、产品型号、错误码、人名等精确匹配较弱；BM25 等关键词检索恰好擅长精确匹配，但无法理解同义表达。混合检索结合两者，提升召回的覆盖面。

融合方式：

  • RRF（Reciprocal Rank Fusion）： 只根据每个结果在各路中的排名计算融合分数，不需要对不同量纲的分数做归一化，简单稳健，最常用。
  • 加权分数融合： 对两路分数归一化后加权求和，需要调权重。

融合后通常再接一个重排模型。

参考：混合检索与重排

11. 什么是重排（Rerank）？为什么不直接用重排模型做检索？ ​

参考答案

重排是在初步检索出几十到上百个候选后，用一个更精确的模型重新打分排序，只把排名靠前的少数结果交给大模型。

常用的重排模型是 Cross-Encoder：把查询和文档拼在一起输入模型，直接输出相关性分数，比分别编码再算相似度的双塔模型（Bi-Encoder）精确得多。

不直接用它做检索，是因为 Cross-Encoder 必须对每个"查询-文档"对单独计算，无法预先建索引，面对海量文档时太慢。所以采用两阶段架构：先用快速的检索召回候选，再用精确的重排提升排序质量。

参考：混合检索与重排

12. 用户的问题表述不清或很口语化，如何提升检索效果？ ​

参考答案
  • 查询改写： 用模型把口语化、带指代的问题改写成完整、明确的检索查询，多轮对话中尤其重要（例如把"那它的价格呢"改写成包含主语的完整问题）。
  • 多查询扩展： 生成多个不同表述的查询分别检索，合并结果。
  • HyDE： 先让模型生成一个假设性的答案，用它的 Embedding 去检索，因为答案和文档在表述上更接近。
  • 问题分解： 复杂问题拆成多个子问题分别检索。
  • 元数据过滤： 从问题中抽取时间、产品、部门等条件，先过滤再检索。

13. 如何在 RAG 中实现权限控制？ ​

参考答案
  • 在建索引时为每个 chunk 写入权限相关的元数据，如部门、角色、文档 ID、可见用户组。
  • 检索时根据当前用户身份，在向量数据库中做元数据过滤，确保只检索到有权访问的内容。权限过滤要在检索层完成，不能依赖提示词让模型"不要说"。
  • 原文档权限变更时，同步更新索引中的元数据。
  • 多租户场景下，可以按租户分集合或分索引，实现物理隔离。
  • 返回引用时，也要再次校验用户对来源文档的访问权限。

生成与进阶 ​

14. 检索到的内容和模型自身知识冲突，或者检索不到相关内容时怎么办？ ​

参考答案
  • 在提示词中明确要求以提供的资料为准，资料没有提及时说明"资料中未找到"，而不是凭自身知识回答。
  • 设置相关性阈值，检索分数过低时视为没有命中，直接走兜底逻辑（如提示用户换个问法、转人工）。
  • 要求模型在回答中标注引用的资料编号，便于用户核实，也便于自动检查是否有无依据的内容。
  • 资料之间有冲突时，可以利用元数据（如更新时间、文档权威等级）排序，或在回答中说明存在不同说法。

15. 什么是 Agentic RAG？和传统 RAG 有什么区别？ ​

参考答案

传统 RAG 是固定流水线：每个问题检索一次，然后生成。Agentic RAG 把检索变成 Agent 可以调用的工具，由 Agent 决定：

  • 是否需要检索（简单问题可以直接回答）。
  • 检索什么、用哪个知识库或数据源。
  • 检索结果不够时，改写查询再次检索，或者分多步检索。
  • 检索结果是否足以回答问题。

优点是能处理多跳问题和复杂问题；缺点是延迟、成本更高，行为更难预测，需要步数控制和更完善的评估。

参考：GraphRAG 与 Agentic RAG

16. GraphRAG 解决了什么问题？什么情况下值得使用？ ​

参考答案

普通向量检索擅长找到"与问题相似的片段"，但不擅长回答需要综合全局信息或多跳关系的问题，比如"这批文档的主要主题有哪些"、"A 和 C 之间通过什么关联"。

GraphRAG 从文档中抽取实体和关系构建知识图谱，有的方案还会对图做社区划分并生成层次化摘要，检索时可以沿关系扩展，或者使用社区摘要回答全局问题。

代价是建图成本高（需要大量模型调用）、更新复杂。适合实体关系密集、需要全局总结或多跳推理的场景；对于普通的事实问答，混合检索加重排通常就够了。

参考：GraphRAG 与 Agentic RAG

17. 长上下文模型出现后，RAG 还有必要吗？ ​

参考答案

仍然有必要，但两者的分工会变化：

  • 知识库的规模通常远大于任何上下文窗口。
  • 每次把大量文档塞进上下文，成本和延迟都很高。
  • 上下文越长，模型对中间信息的利用越容易变差，噪音也会干扰回答。
  • RAG 天然支持权限过滤、增量更新和来源引用。

长上下文的价值在于让 RAG 可以更"宽松"：检索更多、更大的块，或者对少量文档直接全文放入。实践中常见的是两者结合。

评估与优化 ​

18. 如何评估一个 RAG 系统？ ​

参考答案

分开评估检索和生成两个环节：

  • 检索指标： 召回率（Recall@K，相关文档是否出现在前 K 个结果中）、精确率、MRR、NDCG 等。需要标注每个问题对应的相关文档。
  • 生成指标： 忠实度（答案是否都有资料支撑，没有编造）、答案相关性（是否回答了问题）、正确性（与标准答案对比）、引用准确性。
  • 端到端指标： 用户满意度、解决率、转人工率。

评估集应覆盖常见问题、边界问题、无答案问题和需要多文档综合的问题。生成指标可以借助 LLM-as-Judge 自动评估，但需要用人工标注校准。

参考：RAG 评估、LLM-as-Judge

19. 用户反馈答案不准，你会如何排查？ ​

参考答案

按链路逐段定位：

  1. 看检索结果： 正确的资料有没有被检索到？如果没有，是文档根本没入库、解析出错、切分不当，还是查询与文档表述差异太大？
  2. 看排序： 正确资料检索到了但排名靠后，没有进入上下文，就需要调整重排或 Top-K。
  3. 看上下文： 正确资料进入了上下文，但被大量无关内容淹没，或被截断了。
  4. 看生成： 资料是对的，模型却理解错了、遗漏了，或混入了自身知识，就需要调整提示词或模型。

关键是有完整的轨迹记录（改写后的查询、检索结果和分数、最终提示词），并把这个问题加入评估集，修复后做回归测试。

20. RAG 系统上线后，有哪些常见的优化方向？ ​

参考答案
  • 数据质量： 清理过时和重复的文档，改进解析，补充缺失的知识。这通常是收益最大的一项。
  • 检索： 调整切分策略、引入混合检索和重排、做查询改写、增加元数据过滤。
  • 生成： 优化提示词，要求引用来源，处理无答案情况。
  • 性能和成本： 缓存高频问题的答案或检索结果，用较小的模型处理简单问题，控制上下文长度。
  • 持续闭环： 收集用户的负反馈和低分对话，分析失败原因，补充到评估集中，每次改动后回归。
